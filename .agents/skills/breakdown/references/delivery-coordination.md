# 交付协调

## 方案模式

列出每项工作的输入、输出、修改边界和真实依赖。依赖注明阻塞的是开始、集成、验收还是发布；共享父项或优先级不是依赖。识别会修改同一文件、接口、schema 或数据所有权的冲突，比较串行与并行的协调成本。

输出共同输入版本、各工作交接条件、集成责任、顺序和统一候选上的重验范围。方案模式不启动 Agent、不修改代码。

## 执行模式

1. 记录基线、目标分支、工作区已有改动和用户所有文件；必要时为隔离工作使用宿主 worktree，不清理未知改动。
2. 固定共同契约与每项工作的唯一修改边界。使用宿主已有委派能力；不可用时按依赖串行执行，不造调度器。
3. 每次交接检查提交/diff、变更文件、实际命令和未决风险；“已完成”文本不是证据。
4. 应用或合并变化前确认候选身份和冲突。接口变化时只调整受影响工作及交接，不重排无关部分。
5. 在同一候选整合结果，检查意外文件、共享接口和数据迁移，并运行与受影响行为对应的最小验证。
6. 返回统一候选标识、已整合内容、验证、剩余限制；到未授权的提交、推送、PR、合并或发布边界停止。

例：两项实现共享一个 schema，先串行确定 schema，再并行调用端和执行端；集成后验证真实调用路径。若宿主无委派工具，顺序执行仍可完成协调。

异常：一个工作返回的 diff 修改了他人边界。暂停该变更，核对原因并局部重新分配；不要为赶进度直接覆盖。
