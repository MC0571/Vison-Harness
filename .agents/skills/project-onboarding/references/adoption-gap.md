# 采用缺口分支

## 新项目

先确认当前阶段真正需要的入口。模糊产品想法可能只需要愿景讨论；代码仓库可能先需要一条真实构建命令和根规则。不要一次生成愿景、架构、ADR、Spec、路线图和 reviewer 全套文件。

## 已有项目

按功能而不是文件名检查：长期目标在哪里、动态工作在哪里、行为约定在哪里、Agent 规则如何加载、命令从哪里来。已有等价材料直接复用，只补无法定位或会造成错误操作的缺口。

## 局部采用

用户只要某一能力时，只接入该能力所需信息。例如只希望规范 PR 审查，可引用现有规则并补审查入口，不要求先建愿景或重排 Issue。

例：仓库已有 `docs/product.md` 作为权威愿景，不创建 `VISION.md`；在项目导航中指向它即可。

异常：GitHub 不可访问时，本地规则与命令仍可确认；动态工作入口标为受阻，不创建 `tasks.md` 代替。
