# 交付协调与集成

读取[共同规则](../../../METHOD.md)及[依赖与协作规则](../../../METHOD.md#4-维护依赖并设计有效的推进方式)。核对本轮工作集合、已有结果、可用执行者、工具与允许动作；只要求协调方案时，不启动实施或修改远端关系。

## 识别可以实际推进的工作

逐项读取本轮承诺及真实前置结果，区分父子归属、优先级、技术依赖与共享修改冲突。每条关键依赖说明缺少什么、阻塞哪个阶段、解除依据及可先做的准备。

不要把集成等待扩大成全部停工，也不要因引用另一项工作就机械添加 blocked-by。条件已满足的工作继续，只有缺少实际消费结果的部分等待。

## 形成可执行的分工

先确定共享接口、语义或生成来源，再选择互不覆盖的工作。为每项明确输入版本、输出结果、修改范围、禁止触碰的共享资源、交接条件和集成责任。没有实际分派时写待分配，不虚构执行者。

宿主具备且本轮允许委派时，传递足够上下文与准确权限，不能只说“各做一块”。宿主不支持子 Agent 时提供明确串行执行顺序或人工交接，不假称并行已经运行。

当共享写入或协调成本超过收益时减少并行。无需为普通内部步骤创建 Issue，也不复制一份权威状态清单。

## 随真实变化局部调整

接口变化、阻塞解除、失败或新证据到达时，只重新安排受影响工作。保留已成立结果；范围不明交给 issue-shaping，设计未知交给 technical-design，证据问题交给 change-verification。

共享文件修改前重读当前版本，不能让各执行者用旧快照相互覆盖。交接结果需直接检查实际 diff、构件或记录，不能只接受“已完成”消息。

## 在同一候选完成整合

按约定顺序集成到准确候选，检查接口连接、状态和兼容边界，运行受影响的整合验证。各分支独立通过不等于组合通过。代码冲突解决后还要核对语义，不把文本合并成功当作交付。

返回已实际完成的协调和集成、当前统一候选、仍受阻部分及责任和下一步。规划完成与真实并行、集成、发布分别报告；没有获准合并或发布时止于该边界。
