# 找到真实测试与运行入口

## 先复用项目事实

查 manifest scripts、构建包装器、Makefile/Taskfile、测试配置、CI 与维护说明；核对执行目录、依赖、参数和环境。区分局部快捷命令与正式门禁，不能凭熟悉程度假定 `npm test` 或 pytest。

读取邻近测试的命名、夹具和隔离习惯，避免未经必要性判断引入另一套框架。已有命令可能执行外部写入，运行前按本轮授权检查。

## 选择最小判别入口

纯计算可用局部检查；跨组件契约需要能够观察交互的入口；关键真实路径需要相应集成/运行检查。构建成功、格式正确、单元测试和真实行为各证明不同事情。

先读取可用基线或运行有意义的检查，区分目标失败、已有无关失败与测试未启动。缺依赖/凭据通常不是产品红灯。

## 没有现成测试怎么办

“不能编造项目命令”不等于“不能构造新检查”。已授权实现或相应诊断时，可以用项目现有语言/运行时、标准库、夹具或隔离脚本建立最小反馈，明确它是本轮新增检查而非已有正式入口。

新增依赖、框架、外部账号或生产探针须符合实际授权与项目规则。仅有只读权限时保持候选不变，说明能够读取的证据和建立反馈需要的最小条件；不要用“缺测试框架”无限阻塞仍可完成的定位。

## 示例

CI 用 `python3 scripts/test_tool.py`，先复用其中目标场景；没有测试但有 Python CLI，可在获准临时目录用固定输入调用 CLI 并断言输出。不能把“启动没报错”当作对原始故障的验证。
