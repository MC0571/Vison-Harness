# 值得保留的测试

## 选观察边界，不冻结内部结构

测试从能辨认目标行为的稳定接口进入。优先选择调用者真实使用的边界；测试纯逻辑或组件内部独立责任时也可以使用较小边界，不要求每个测试穿过整套系统。

判断：实现完全替换但契约不变时，这个测试是否仍应成立？若仅因私有字段、辅助函数名称或无关调用顺序变化就失败，它可能冻结了实现。

不能为了“只测接口”忽略持久化、事务或外部协议。持久化是承诺时，应通过合适读取/重启路径检查；低层存储适配器自身的集成测试也可直接检查其契约。观察点取决于所测责任，不一律禁止数据库断言。

## 期望必须能与实现不同意

| 弱检查 | 问题 | 更有判别力的做法 |
| --- | --- | --- |
| 期望值再次调用被测算法 | 实现和断言可以一起错 | 使用确认例子、独立手算值、参考实现或不变量 |
| 只断言返回对象存在 | 原错误也可能返回对象 | 断言目标字段、结果与必要副作用 |
| 只验证内部方法被调用 | 方法被调不证明行为正确 | 观察结果；协议调用本身是契约时才检查交互 |
| 从当前输出自动更新大快照 | 把新缺陷当成正确答案 | 审查每个与承诺有关的变化，缩小快照范围 |
| 只在修复后运行 | 可能从未抓住缺陷 | 在可用旧候选/复现上确认判别力，或准确说明限制 |

示意：测试折扣时，`expected = production_discount(price)` 不是独立答案；已确认“100 元按八折为 80 元”的固定例子可以。更多输入可检查确认的不变量，但不能凭空推导业务折扣上限。

思考一个具体错误实现：跳过持久化、重复扣费、忽略权限、按错误顺序排序。测试会不会仍然通过？不需要每次运行变异测试，也应做这个轻量反例检查。

## 替身选择

- 真实实现：成本、确定性与副作用可控时优先，尤其当目标就是集成行为。
- Fake：简化但保持所依赖语义；内存存储不自动证明真实事务、锁或持久化。
- Stub：为一个边界提供固定响应，适合选定错误或时间条件。
- Mock/交互断言：用于请求形状、协议顺序或外部副作用本身就是承诺的场景；不遍历模拟每个内部合作者。

如果把被测路径全部替换成 mock，就只验证了测试脚本。替身不能吞掉本次要检查的失败机制；真实依赖缺失时收窄结论，而非声称集成通过。

例：发送支付请求的字段是协议契约，可以断言该边界的请求形状；而业务计算函数内部调用某私有 helper 几次通常不是契约。

## 确定性与隔离

在风险相关处控制时间、随机种子、外部响应、文件路径和共享状态。每个测试拥有可清理的数据，既能单跑也不污染其他测试。并发故障可保留频率与条件，不把偶然一次绿色当成稳定修复。

重用夹具时保留测试可读性：读者应能看懂输入、动作和期望，无需追踪多层隐式初始化。一个测试可有多个断言，但它们应服务同一个可理解行为，不硬性“一测试一断言”。

## 何时足够

测试应覆盖本轮承诺及其可信失败方式，不追求固定金字塔比例、分支覆盖率或每个边界独立文件。测试边界由工程判断选择，只有涉及未定产品保证或扩大副作用时才需要用户决定。

对当前未覆盖的高影响行为明确保留缺口；对无关远期可能性不新增测试。代码行数、测试数与全绿都不能替代这种判断。
