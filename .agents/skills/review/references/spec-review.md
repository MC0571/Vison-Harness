# Spec 审查：寻找可成立的反例

固定规格版本、确认范围与相关决定。重点不是它是否像某个模板，而是它能否区分符合与违反目标的实现。

## 分析

先提取角色、概念、前置条件、事件、结果、不变量与适用边界，再核对当前承诺是否都有表达。根据具体语义检查失败、重复、顺序、权限、兼容和必要质量保证；不添加无依据要求。

双向检查：确认要求是否遗漏；新增条款是否来自有效决定，还是实现偏好或推测性功能。必要可观察顺序可以是契约，内部操作方法无需全部固化。

## 构造反例

试着描述一个满足现有文字却仍让目标失败的实现。例如“超时后标记终态”未说明持久化时，重启后可能再次运行；只有产品确实承诺跨重启终态时，这才是需要补足的语义。

反例必须基于确认范围，而非创造全新需求。正常结果、异常和相邻行为同时适用时应相容。

## 冲突判断

对齐对象、范围、版本和时间后再判断。相邻规格同名概念可能属于不同上下文；工作项的当前切片与长期规格可以不同。只有同一场景下无法同时成立才是真冲突。

未知产品取舍由用户决定，不能以偏好的技术方案补空白。文风、章节数或合理实现自由不构成缺陷。

## 输出

问题说明位置、字面允许的错误行为、触发场景、违反的确认目标、影响与最小语义修正。无实质问题可接受；缺必要来源则准确限制判断，不强迫生成缺失文件套餐。
