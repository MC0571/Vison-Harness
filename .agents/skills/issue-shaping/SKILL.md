# 单项工作整理

先读取[共同规则](../../../METHOD.md)及相关 Issue 的完整正文、评论中的有效决定和关联规格。用户只要求整理建议时，不写入；已授权维护目标 Issue 时，在该范围连续完成，不再请求形式许可。

## 找到本项工作的边界

识别它是调查、规格、功能、缺陷、重构、交付还是长期能力。沿已有愿景和父级工作说明它为什么存在，不将父级全部承诺塞进本项。已清楚的 Issue 直接复用，不为调用本 Skill 重新改写。

对含糊内容先查可查事实：缺陷的实际表现和复现条件、已有行为约定、受影响调用者、当前版本。只有答案会改变范围且无法从现有事实确定时，才询问有权作取舍的人。不要把自己的实现偏好写成产品决定。

## 形成可接手的承诺

用项目已有结构说明用户结果、当前范围、明确边界、关联 Spec、完成条件和仍未决的问题。功能应说明可观察结果；调查应说明要回答的问题及结束条件；重构应说明必须保持的行为；缺陷应区别预期与实际表现。不规定统一标题套餐。

完成条件须覆盖当前承诺，而非仅写“测试通过”。对已有下层工作做反向检查：全部完成后，本项是否仍缺入口、整合、持久化或交付结果？发现缺口先指出，不通过转移工作暗中缩小原承诺。

复用已有长期能力容器记录暂缓内容。只有确需独立安排、协作或接受的结果才拆子 Issue；普通编码步骤留给实施过程。父子归属、优先级、技术依赖和共享文件冲突分别表达。

## 落实与交接

获准写入前重读目标与原生关系，保留无关正文和历史。查询等价对象后才创建；结果不明先查询，不能盲目重试。更新后回读内容和必要关系，不将正文中的引用冒充原生 parent 或 dependency。

若缺少会改变承诺的产品决定，只暂停依赖该决定的部分。范围已充分时交给相应实施或设计工作，不重新启动 Vision 或 Breakdown；跨越多个交付批次的整体重排才交回 Breakdown。

返回本项可执行的范围、完成条件、来源、实际修改或零写入结果及下一步。整理完成不代表实现完成，不自行关闭功能或长期能力。
