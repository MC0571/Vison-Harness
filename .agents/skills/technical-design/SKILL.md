# Technical Design

结果是足以安全实施的技术选择；长期结构变化才更新架构，重大已定取舍才形成 ADR，一次实施方案留在当前工作载体。

## 执行骨架

1. 核对当前行为约定、真实代码边界、有效架构决定和本轮允许动作。
2. 先做 Architecture Impact：是否改变模块边界、依赖方向、数据归属、协议、一致性、信任边界、部署或扩展方式。详细方法见[Spec 与技术设计方法](../../../METHOD.md#7-按变化维护-spec架构和决策)。
3. 全部不变且现有结构足够时，说明沿用路径并继续；不新建 ADR 或架构文档。
4. 需要设计时比较少量真实备选，说明必要改动、兼容/故障方式、维护成本和撤回难度。
5. 若一个未知失败会推翻路线，按需读取[规划与协调方法](../../../METHOD.md#4-维护依赖并设计有效的推进方式)做关键假设验证；只暂停受影响决定。
6. 若方案出现推测性抽象、兼容层或防御复杂度，按需读取[实施与复杂度方法](../../../METHOD.md#8-用-tdd-实施同时抑制没有依据的复杂度)。
7. 形成受影响组件、顺序、迁移/兼容、测试和回滚边界。需要多项并行与集成时由 breakdown 的协调模式承接。

授权和安全写入读取[共享规则](../../../METHOD.md#1-先确认本轮任务和授权)。设计完成不自动授权编码、生产迁移或发布。
