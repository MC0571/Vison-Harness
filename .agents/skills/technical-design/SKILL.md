# 技术设计

读取[共同规则](../../../METHOD.md)及[行为、架构与审查规则](../../../METHOD.md#7-按变化维护-spec架构和决策)，核对当前范围、相关 Spec、真实代码边界和有效架构决定。只要求方案比较时，不写代码或创建实施任务。

## 先判断是否需要新设计

检查本次是否改变模块边界、依赖方向、数据归属、协议、一致性、信任边界、部署或扩展方式。全部不变且既有结构足够时，直接指出沿用路径，无需新架构文档或 ADR。

对受影响结构追踪输入、处理、持久化和调用者，说明谁拥有关键状态和失败恢复责任。业务语义复杂时沿用领域术语与不变量；不为展示 DDD 创建没有实际职责的层、服务或聚合。

## 比较真实可行的方案

以已确认行为和约束比较少量实际备选，列出必要改动、兼容影响、故障方式、维护成本与撤回难度。不能用“更先进”“生产级”作为复杂化的依据。已有实现也是一个候选，不为重构而排除它。

发现会改变路线的关键未知时，将明确的问题交给 assumption-validation；未影响的设计可继续。产品取舍未决定时返回有权者，技术偏好不能改写用户目标。

## 安排安全实施

对需要方案的变化，确定受影响组件、可独立交付的行为切片、接口约定、变更顺序和风险。涉及数据或外部兼容时说明迁移前提、过渡行为、旧版本共存限制、失败处理与回滚能力；不可逆步骤要明确，不能虚构可回滚。

有并行价值时先明确共享契约与修改边界，再交给 delivery-coordination 安排集成。测试策略针对行为与迁移风险，不以罗列所有检查代替判断。

## 把事实放在正确位置

已授权的一次实施方案写入现有 GitHub 工作；长期结构变化更新架构；重大已定取舍才记录 ADR 及其替代关系。未决定的选项继续留在讨论中。三类产物均非必选，不生成固定套餐。

写入前重读并保留无关内容，写后回读。返回选择及依据、影响、可开始的工作和真正阻塞的决定。设计完成不自动授权实施、迁移生产数据或发布。
