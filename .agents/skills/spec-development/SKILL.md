# Spec Development

交付的是当前变化需要的长期行为约定，或“已有约定足够/无需修改”的明确结论。

## 执行骨架

1. 从用户请求、当前工作和有效决定取得范围；不能从现有代码或测试反推应该承诺什么。
2. 判断本次是否改变可观察行为、状态、领域数据、接口、权限、安全、失败、兼容或必要非功能保证。需要详细判断时读取[Spec 与技术设计方法](../../../METHOD.md#7-按变化维护-spec架构和决策)。
3. 优先复用已有语义边界；只有独立验证、复用或演进价值的内容才拆成新规格对象。纯重构且约定未变时明确零 Spec 修改。
4. 写出能区分满足/违反的行为、失败与不变量；把未决产品取舍保留为未决，不用实现偏好补答案。
5. 与相邻约定检查术语、状态、所有权、权限和兼容冲突。只在获准时完整读取目标、最小修改并回读。

授权和治理充分性读取[共享规则](../../../METHOD.md#1-先确认本轮任务和授权)。

## 边界

Spec 不保存进度、负责人或里程碑，不把技术方案写成产品要求。用户只授权审查时使用 review，不要在本入口边审边改。规格完成不等于实现完成。
