# Vision 行为规格

## 用途与边界

Vision 帮助用户形成、审查、复用和按授权修订足以支持当前规划的项目愿景。它不替用户决定产品方向，不自动创建实施事项，也不把当前交付缩成完整产品。

通用授权、事实和质量规则见 [METHOD.md](../../METHOD.md)。具体交付拆解由 [Breakdown](../breakdown/spec.md) 承担，项目来源定位与会话接续由 [Project Context](../project-context/spec.md) 承担；本规格不复制它们的规则。

## 读取当前项目，而不是 Plugin 的项目

开始时识别本轮请求是形成、检查还是修订，允许修改什么，结果交给谁。读取用户已给出的信息、适用项目约定和相关产品材料；不重复询问已经明确的答案。

必须区分使用 Vision Harness 的项目与提供方法的 Plugin。随包的 METHOD、Spec 是方法依据，不是用户项目的愿景。项目已有组织级愿景或其他明确权威入口时，引用并使用它，不强制另造本地 VISION.md。来源不明时只澄清影响当前决定的缺口。

材料中的提案、例子、旧决定和推测保留各自身份。不能仅因某段文字出现在仓库、PR 或聊天摘要中，就将它升级为已确认需求或新的写入授权。

## 形成足以规划的愿景

愿景应让读者辨认主要使用者、重要问题、预期结果、已知主要能力、产品边界、明确非目标、成功表现和关键未知。这些是需要表达的含义，不是固定标题、长度或必须逐项询问的问卷。

已有输入足够时直接整理、引用或给出可继续的判断。输入有关键歧义时，说明歧义将改变哪个决定，并提出最少必要问题或有依据的备选解释。未知允许保留，不能为了填满模板而编造需求、量化指标、收益或期限。

完整的是当前确认的目标与边界，不是所有远期技术细节。已知而暂不实施的能力保留其目标身份；尚未采用的宿主、界面或技术选择不能自动成为产品限制。当前实现形式也不能反向缩小目标。

用户只要求探索方向时，可以输出假设、选项和待决定问题；不得宣称已得到可用于完整实施的确定愿景。愿景足以支撑当前决定时停止扩展访谈，不要求先写全 Spec、架构或所有交付批次。

## 审查、复用与修订

审查区分文字难懂、产品目标缺失、相互矛盾和仍可保留的未知。没有实质缺口时，应复用现有愿景，不为体现工作量重写。

新证据影响目标时，指出受影响的目标、边界或成功判断，区分事实、推断和建议；说明仍有效的内容与可能需要调整的规划。停止某条实现路线不自动取消它承担的需求，取消需求本身需要相应决定。

修订以当前完整内容为基础，仅改授权范围，保留无关内容和有效目标。已接受目标的实质改变必须有决定依据；不能为了让当前实现通过验收而降低愿景。重要决定历史由项目既有 Git/PR/Issue 记录承载，不在愿景里维护进度或第二份任务表。

本阶段不要求自动完成跨所有历史工作的迁移；影响范围应明确，并由对应获准工作承接，不能静默遗忘。

## 写入与交接

只要求建议或检查时不写文件或 GitHub。授权写愿景不等于授权创建路线图、工程子任务、代码、PR 合并或发布。已有明确委托覆盖本次动作时，在范围内连续完成，不逐项重复索取相同许可。

按项目已有约定选择写入位置；不存在既定入口且获准在仓库维护愿景时可使用 VISION.md。写前读取完整内容、处理并发变化，写后回读；无法完整读取或结果不明时不盲目覆盖或重复操作。共享安全写入原则复用 METHOD，不自行声称具备原子更新保障。

给后续规划的交接至少能辨认愿景的权威位置、适用版本或读取依据、确认目标与未知、与本轮有关的有效决定，以及允许继续到哪里。已有文件与 GitHub 记录可以表达这些信息，不要求新建交接状态文件。

如果只形成建议稿，应明确未接受或未写入；下游不得将它当作用户已批准的完整范围。只有愿景已具备本轮所需依据且规划动作在授权内，才衔接 Breakdown；没有后续授权时交付愿景结果即是正确终点。

## 结束与验证

分别报告愿景是否足以支持当前任务、实际修改了什么、保留了哪些未知、还有哪些决定或操作未获授权。文件写入成功不等于用户已接受产品方向，愿景接受也不等于功能已实现。

采用模糊意图澄清、充分材料复用、局部授权写入、已有入口、路线变化和无须修改等正反场景验证。具体案例和组合验证要求见 [项目启动验证说明](../../evals/project-startup/README.md)。结构检查不能代替真实 Agent 行为；本文件不保存工作状态或验收日期。
