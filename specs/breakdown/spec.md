# Breakdown 行为规格

## 用途与边界

Breakdown 把足以支持规划的愿景，转换为用户能判断、后续 Agent 能接手的产品交付安排，并根据已有事实滚动细化或修订规划。

它支持初始拆解、下一批次细化、已有规划审查与修订。输出可以是建议，也可以在明确授权和工具支持下落实到工作系统。它不代替用户决定产品方向，不实现规划中的产品功能，不擅自合并、发布或迁移整个项目。

通用授权、事实维护、规格、架构和证据原则见 [METHOD.md](../../METHOD.md)；本文件规定 Breakdown 的可观察行为，不规定固定 Skill 数量、宿主命令或文件套餐。

## 输入与当前依据

开始时辨认本轮请求、允许的副作用、当前任务范围，以及项目已有的愿景、有效决定、产品形态、工作安排和相关完成证据。

必须区分用户已确认的目标、候选方案、待验证假设、未知、暂缓工作与明确不做的方向。已有材料足够时直接使用，不要求用户重新说明已知内容。材料中的提案、历史评论和示例不自动成为当前授权。

只恢复支撑当前决定所需的上下文。发现跨范围影响或事实冲突时再扩大读取，不把每次规划变成全仓调查。

若缺口会改变当前产品边界或下一步决定，指出具体缺口、影响和最少必要问题。无关的远期未知不得阻塞当前规划。用户明确要求探索或只讨论高层方向时，允许给出相应粒度的有界建议，不宣称已形成可实施的完整计划。

## 对象含义

| 对象 | 必须表达的含义 |
| --- | --- |
| 愿景 | 长期问题、希望发生的变化与产品边界 |
| 阶段目标 | 当前阶段重点达成的结果，不替代完整产品目标 |
| 结果证据 | 用什么观察或验证支持结果；计划采用的验证方式不等于已经取得证据 |
| 产品组成 | 哪些具体入口、组件、包、接口、材料或其他交付物承担目标 |
| FR | 用户或系统需要获得的功能行为；由 Issue 或项目已有载体维护 |
| Milestone | 一组具体交付共同形成的阶段结果、范围和验收条件 |
| 工作项 | 为某项承诺开展的探索、规格、实现、验证或集成工作 |

这些对象不要求一一对应，也不要求形成固定层数。一项 FR 可以跨组件，一个共享组件可以支持多个目标。父子关系是主归属，不自动表示贡献关系或执行顺序。

可以借鉴 OKR 的目标与结果区分，但不得把任务数量当作效果，或为没有基线的效果编造百分比、期限和收益。产品不可缺少的授权、正确性与安全约束，不能用其他指标的高分抵消。

## 初始拆解

### 全景与产品组成

在宣称完整产品规划可用前，必须使已确认的主要目标与主要产品组成保持可见。每个已确认目标都有承担方式或明确的待决定事项；未知标为未知，不靠发明需求补齐表格。

必须按实际产品形态拆解。Plugin 可以由 Skill、必要参考材料、打包入口、工具或经论证的 Hook 承担；库或应用应使用它们自己的产品对象，不强行列 Skill 和 Hook。

候选组成须标为候选并说明待决定部分；不能以“避免提前设计”为由一直不说明主要交付物，也不能将候选实现方式自动升级为需求。

不以方法章节数决定 Skill 数量，不以创建目录或文件证明功能可用。已确认但本轮不实施的目标由现有适合的工作项承接即可，不为每个细节新建 Issue。

### 阶段与近期交付

每个近期 Milestone 必须能说明用户或上游系统可以通过什么入口获得什么结果、由哪些交付物共同提供，以及如何验证。未来阶段可以较粗，但不能只有“完善能力”之类无法辨认产品结果的名称。

近期 FR 和工作项必须说明交付对象、行为范围、与已有目标的联系、相关约束、完成证据及下一步是探索、Spec、设计还是实现。精确行为复用相应 Spec，不在多份正文中复制维护。

更远工作不提前拆到文件、函数和内部测试步骤。不得把整个能力未完成当作当前有限但合格版本不能交付的理由，也不得用切片完成自动关闭上层完整承诺。

### 依赖与并行

依赖必须说明缺少什么结果、阻塞哪个阶段、如何解除；优先级、共同父项或共享目标本身不是依赖。

能先做调查、规格或独立实现的工作，不因后续集成依赖而被整体锁住。原生关系不能表达阶段限制时，用对应工作项中的简短说明表达，不制造错误的整体阻塞关系。

并行安排必须说明共同约定、各自输出和修改边界，以及集成责任、顺序和统一候选上的重验范围。无法确定具体负责人时指出待分配的责任，不编造人员或已有分派。

若关键假设会推翻路线，先安排有界验证。正常适配成本不等于不可行；需要突破已确认职责的缺口不能被隐瞒。工具或人力的共享冲突应被辨认，不以并行 Agent 数量衡量效率。

## 下一批次细化

读取已有规划、相关交付事实和新决定后，辨认变化对象、版本、范围与时间。只增加支撑下一批工作所需的细节，并解释发生变化的部分。

保留仍有效的目标、工作身份、已有证据和不受影响的安排。对解除的依赖及时调整；对新约束指出受影响范围；不围绕已实现部分缩小产品，也不从头再造一套规划。

没有新事实且现有规划可用时，应给出无需修改的结论或直接指出已有下一步，不以生成更多 Issue 或文字证明工作量。

历史与当前快照不一致不必然是冲突。无法证明某项完成或授权时，说明缺少的证据，不从状态标签推导功能完成或新增权限。

## 已有规划审查与修订

先区分措辞难懂与产品拆解缺失。若只有抽象能力、或标题加了 Skill 而正文仍没有可观察行为和验证，不能仅润色标题就宣布修复。

审查必须分别回答：

1. 已确认的主要目标是否有归属，是否误增或丢失目标？
2. 具体交付是否清楚，下一位 Agent 能否不重新定义产品就接手？
3. 若所有下层工作都按现有条件完成，上层承诺是否仍可能明显不成立？若是，指出缺少的集成、入口、行为或验证。
4. 当前阶段的证据计划是否支持它准备宣称的结果？
5. 关系与状态是否被正确表达，并与本次实际操作相符？

配置正确只能支持第 5 项的相应部分，不能代替其他判断。对只有组件清单却缺少用户结果的计划，也应指出问题。

修订建议应区分保留、修订、拆分、合并、替代和停止，并解释理由、旧目标承接方式及历史保留。只改变受影响内容；不先清空旧规划，也不将旧编号偷换成完全不同的承诺。

审查允许多种合理的树、标题、顺序和组件划分。没有违反承诺的风格差异不构成阻断；本轮不需要的复杂检查不得成为新的前置条件。

## 获准写入与失败处理

只要求建议或评估时，不产生仓库或工作系统写入。已有明确规划写入授权时，在允许范围内连续推进，不逐项重复索取相同确认；跨到代码、合并、发布或全局迁移时另行检查授权。

写入前读取完整当前对象并检查已有等价事项。优先复用；冲突时保留他人修改并处理受影响部分，不用旧摘要覆盖全文。需要的能力不存在时准确说明，不提升权限或另造权威状态库。

写后回读正文、原生关系和适用状态。响应超时或结果不明时先查询效果，再决定重试；不能盲目重复创建。不具有条件更新能力的工具不得被描述为保证原子一致性。

如果只完成部分写入，报告已完成、未确认、失败与尚未执行的具体对象。文字引用、模拟工具结果与原生关系分别表达；未回读成功的结果不宣称成功。

## 输出与结束

完整规划输出应让用户无需重读全部历史即可找到：当前依据与授权、主要目标与产品组成、阶段结果和证据计划、近期 FR/工作、依赖与并行、未知和暂缓、下一步及停止边界。具体格式可以适配项目，不要求固定表格数量或统一字段名。

报告分开给出目标覆盖、产品规划可用性、GitHub 操作结果。纯建议模式下，GitHub 写入应标为未请求/未执行，而不是通过或失败；无法验证时说明限制。

只有与所请求粒度相称的目标、交付、依赖和验证安排已经足够，才称本次规划可用。信息不足时只阻塞受影响决定；信息足够时停止扩展前置工作。规划完成不代表产品已实现，也不自动产生下一批实施授权。

## 验证方式

采用固定输入的正反行为场景和实际宿主中的候选运行验证。初始拆解、下一批次细化与规划修订均需覆盖；至少包含一种非 Plugin 产品。场景不是唯一正确答案树。

工具与格式检查可验证确定性结构，但不能单独判定规划语义质量。实际验收应由与实现判断分离的审查读取原始输出和副作用证据，并限定到候选版本、环境、输入与覆盖范围。

验收设计和样例见 [Breakdown 验证说明](../../evals/breakdown/README.md)。它们是本规格的验证投影，不是另一份当前项目规划或状态。
