# Review 工作的行为约定

## 适用对象与授权边界

本约定适用于对 Spec、代码实现和 Pull Request 候选形成审查判断，无论 Review 被直接请求，还是由其他工作按条件衔接。Review 的结果是对准确候选给出有依据、有限范围的判断，不是自动修改被审查对象、执行合并或替用户作产品取舍。

审查授权与修复、实施、合并、发布授权分别成立。用户只要求审查时，即使工具具备写能力或问题显而易见，也不得修改候选。用户同时明确授权修复时，审查结论仍先独立形成，再由实施入口处理获准修改；不能通过边审边改让原候选失去可审计性。

## 证据与候选

审查必须绑定准确对象、版本和范围。作者摘要、旧 head 的结论、文件存在、CI 绿色或测试数量都不能自动替代对当前候选的直接读取。

只读取支持当前判断需要的上下文。材料被截断、关键来源缺失或版本不确定时，应限制结论并说明缺口；不能为了给出确定答案而猜测完整内容。已有证据可以复用，但要说明当前变化为什么没有影响它支持的结论；受影响部分才补审或补验。

实施者自检、自动检查、独立审查和最终接受是不同判断。独立审查必须直接读取候选与依据并自行形成结论，不能只更换角色名称后复述实施者摘要。

## 三类审查

### Spec

核对当前承诺是否被准确表达；行为、状态、失败、权限、边界和必要兼容语义是否清楚、相容、可验证；是否把技术方案冒充产品要求，或擅自扩大/缩小承诺。

审查应尝试构造“实现符合字面但仍违反用户结果”的反例。排版、标题套餐和合理实现自由度不构成阻断。

### Code

从 diff 和真实入口追踪受影响行为，检查与 Spec/本轮承诺的一致性、状态和数据所有权、权限与输入保护、错误传播、资源生命周期、并发/重试/取消、兼容边界以及无依据复杂度。

测试通过只支持其覆盖的行为。审查应区分本次新增回归与不相关旧问题，不用风格偏好、无法证实的猜测或可由确定性工具处理的问题制造阻断。

### Pull Request

核对当前 head 与有效范围，判断已有 Spec/代码审查和验证是否仍覆盖当前候选，区分技术条件、证据充分性和实际操作授权。

PR 审查不机械重做全部前序工作；只补当前变化影响的部分。审查通过不自动授权合并、发布或关闭长期能力；需要合并后回读或验证的工作不能因自动关闭语义提前宣布完成。

## 结果与后续

每个发现应说明位置或对象、触发条件、违反的依据、影响及最小修正方向。阻断、非阻断建议、未检查范围和证据限制分开表达；没有发现阻断可以是正常结论，不要求为了体现工作量凑问题。

候选变化后只重审受影响部分。只在获准时把审查结果写入既有 PR/Issue；Review 本身不修改 Spec/代码、不合并、不发布。

验收应覆盖三类对象、review-only 不修改、旧证据适用与失效、候选变化的局部重审、没有问题的正常结束，以及证据充分但缺少合并授权时仍停在操作边界。
