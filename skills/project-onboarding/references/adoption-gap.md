# 按职责识别采用缺口

## 先限定采用面

从用户本次要使用的能力出发。只接入 PR 审查，需要候选、标准、相关行为依据和审查入口；不因此要求完整愿景、路线图或所有 Spec。新项目若只有产品想法，当前结果可以只是能继续愿景讨论的入口。

## 等价、补充、冲突与缺失

| 观察 | 判断方法 | 最小动作 |
| --- | --- | --- |
| 名称不同，维护同一事实且语义相容 | 比较职责、范围和权威身份，不比较标题 | 复用并补导航（确有必要时） |
| 一份是规则，一份是自动生成视图 | 判断是否存在两个手工权威源 | 保留派生视图，指向真正来源 |
| 根规则通用，局部规则有明确例外 | 核对适用范围与宿主优先级 | 保留有效差异，不合并成全仓约束 |
| 同一对象在相同范围下有相反要求 | 比较有效决定、版本和实现入口 | 局部报告冲突，不能靠复制文件解决 |
| 资料存在但当前入口无法定位 | 能否给后续 Agent 一个准确读取地址 | 只补导航 |
| 当前必要行为没有决定或依据 | 区分能查事实与产品取舍 | 先查事实；只等待真正影响当前选择的决定 |

不要用“找不到预期文件名”代替缺口证据。也不要因已有文件很长就判定其内容充分。

## 对命令保持语义区分

README 的快速测试与 CI 的发布测试可能都正确；只有确认其针对相同目标而其中一条已失效，才提出修正。先查配置、脚本和使用目录，必要且获准时执行最小检查。不将未经运行的命令写成已验证可用。

## 应用与结束

在既有权威载体修正，不搬迁全仓、不增加平行状态。每个改动都应能回答“缺它会造成哪种当前错误”。当前能力所需入口已足够时停止，剩余无关采用面不成为前置条件。

例：已有 ADR 记录历史选择、架构文档记录后来替代的结构，两者并不因措辞不同而冲突。只在当前入口仍误指向旧选择时修正引用。

工具受限：GitHub 不可访问时可完成本地入口检查，报告动态工作部分未核对；不创建 `tasks.md` 假装接入完成。
