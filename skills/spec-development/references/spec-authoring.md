# 从确认需求形成可判断的行为规格

## 建立最小语义模型

从当前确认范围提取概念、角色与责任所有者；不要用某个实现类替代领域概念。每条行为连接：

> 前置状态/条件 → 事件或请求 → 可观察结果/状态变化 → 不变量与失败约束。

“可观察”包括调用者依赖的错误、状态、数据效果和时序，不只包括 UI。某些顺序本身是契约，例如写入前授权、回答后才作依赖回答的决定；不能因为看起来像步骤就删除。

## 按语义选择覆盖维度

| 信号 | 要辨认的问题 | 何时不展开 |
| --- | --- | --- |
| 身份或对象关系 | 同一对象如何辨认，谁拥有生命周期？ | 与本次变化没有关系时 |
| 状态变化 | 合法前置状态、终态、拒绝和恢复是什么？ | 无状态行为不造状态机 |
| 重复/重试 | 重复输入的结果与副作用；幂等边界是什么？ | 没有相关保证时不擅自增加幂等承诺 |
| 并发/顺序 | 哪种竞态可能违反不变量，冲突如何呈现？ | 真实环境与契约均排除时 |
| 错误/部分成功 | 哪些效果已发生，失败如何暴露，能否重试？ | 不列与当前行为无关的故障大全 |
| 权限/数据 | 谁能对什么操作，拒绝时不得发生什么？ | 不新建无需求依据的角色体系 |
| 兼容/协议 | 哪些支持对象受影响，旧输入和输出怎样处理？ | 私有变化没有兼容承诺时 |
| 必要质量性质 | 哪个操作在何种环境/负载下必须满足什么？ | 不凭“生产级”自动填性能或可用性数字 |

这是思考索引，不是强制文档套餐。只有当前承诺真正触及的维度才进入规格。

## 典型场景、反例与可区分结果

先写正常场景，再选最能区分两种实现的边界情况。期望来自确认意图、契约或已作决定，不来自当前代码恰好怎样运行。

模糊：“任务必须可靠超时。”

更明确：“达到已配置期限时，运行实例进入 `timed-out` 并持久化。迟到的成功结果不得使它进入 `completed`。通知失败不回滚已经发生的终态转换。”

反例检查：“只在内存修改终态，重启后恢复为运行中”符合‘超时了’的口头描述，却不符合持久化承诺。应补结果语义，而不是直接要求某数据库事务实现。

另一个例子：“重复创建不会重复扣费”需辨认同一请求的身份、重复请求返回什么、扣费已发生但响应丢失时如何处理。尚未决定身份窗口时保留问题，不靠实现者默认 TTL 代替需求。

## 双向覆盖而非条款计数

从本次确认范围逐项找到语义表达，找出缺失或只覆盖正常路径的部分。再从新增条款反查依据，识别把推荐技术、推测性功能或测试便利写成需求的情况。

既有条款可以直接引用，不复制全文。覆盖检查可在当前工作上下文完成，不新增永久需求状态表。远期确认能力由工作图承载，本 Spec 只维护相关长期语义。

## 跨规格冲突

1. 对齐对象、版本、范围和术语；同词异义先澄清语义归属。
2. 构造一个同时适用两条约定的场景；无法同时满足才是真冲突。
3. 区分仍有效旧决定、已经被替代的规则、工作切片边界与长期保证。
4. 产品取舍按有效决定处理；不为了迁就当前实现单方面降低保证。
5. 更新唯一权威条款及必要引用，保留决定历史，不维护两套竞争的行为定义。

例：Issue 只承诺本轮实现持久化，不等于可以从长期超时规格删除通知。工作完成条件与产品行为不是同一种事实。

## 写入与完成

只因语义变化修改 Spec，不因进入下一工作状态修改。能区分正确/错误实现、必要异常与相邻边界清楚、剩余未决项已准确标明时结束。无需大段代码、固定指标、工作编号或实现步骤。
