# 有依据的复杂度与真正的简化

对新抽象、适配、兼容、防御和流程要求，辨认它服务的确认需求、可信风险或维护需要，再比较更简单的结构。风险不必已造成事故才成立，但“以后可能有用”本身不是足够依据。

## 判断负担，而不只数文件

| 检查 | 要问什么 | 可能动作 |
| --- | --- | --- |
| 删除测试 | 删除这一层后，复杂度消失还是散落到调用者？ | 前者考虑内联；后者可能应保留集中责任 |
| 知识负担 | 调用者必须理解多少顺序、状态和内部细节？ | 隐藏技术编排，保留真实业务选择 |
| 变化局部性 | 同一规则是否必须在多处重复修改？ | 让规则回到其所有者，不仅搬到另一个大文件 |
| 真实变化 | 哪项当前差异需要这个扩展点？ | 无真实需要时就近实现；有测试/隔离价值时也可保留单实现边界 |
| 兼容退出 | 哪些对象仍获支持，何时可删除旧路径？ | 有限过渡，不默认永久双写和多模式 |
| 流程价值 | 这项检查防哪种错误，何时触发和结束？ | 删除无影响检查，不删真正风险控制 |

这些是判断手法，不是阈值。不能用“第三次重复必须抽象”“只有一个实现就不得有接口”代替语义判断。

## 选择最小正确结构

先找标准库、平台能力与已有依赖，避免平行机制。行为属于同一所有者且一起变化时适当集中；不同职责不能为了减少文件而混合。薄包装可能承担权限、隔离、兼容或生命周期约束，删除前先辨认它的存在理由。

重复条件可能说明缺少明确模型，也可能只是两个合理局部判断；先比较其变化原因与不变量，再选择共享规则、类型边界或局部实现。不要一看到条件语句就换成 Strategy/Factory。

必要安全、权限、输入校验、数据完整性、可访问性和可信故障恢复不能以“简单”为名删除。受控内部路径可以依赖已建立契约，但必须确实存在该契约。

## 简化过程

先固定不能改变的行为；识别有依据的目标负担；选择局部可逆变化；检查负担是否真正减少，还是被转给调用者、运维或用户。没有净收益时零修改。需要大范围重构时明确授权与范围，不借当前小改动顺手扩大。

例：唯一固定映射直接使用局部字典，没必要创建注册中心。多个调用者都必须重复维护同一权限顺序时，集中该规则可能减少负担，即使增加一个文件。

反例：把两个数据所有者的逻辑塞进一个文件虽然减少文件数，却破坏责任；应删的是推测性包装，而不是必要边界。

对 Review：复杂度问题须说明具体负担、现实影响和保留正确性的更小替代；仅“我更喜欢另一种写法”是偏好，不构成阻断。
