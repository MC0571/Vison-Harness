# 模块与接口：把复杂度放在合适的位置

## 接口不是只有签名

接口是调用者正确使用一项能力必须知道的全部内容：输入输出、状态与顺序、不变量、错误、配置、副作用以及必要性能保证。一个函数可以签名很短，却要求调用者先后调用五个内部步骤；它并不一定简单。

这里的模块是拥有接口与实现的责任单元，可以是函数、包或跨层能力。沿用项目已有语言，不强制把所有“服务、组件、边界”改成同一术语。

## 由真实使用场景反推边界

1. 选当前确认的正常操作和一条关键失败路径，列出调用者必须知道、决定和重复处理的内容。
2. 区分领域决定与技术细节：决定由正确的责任方拥有，重复技术编排尽量隐藏。
3. 将因同一原因变化、维护同一不变量的逻辑放在可控位置；真正有独立责任和变化方向的部分保留边界。
4. 用第二个真实调用场景检查是否减少调用负担；不要用假想十种未来实现证明抽象必要。
5. 说明错误与副作用怎样跨接口可见，测试如何从合适观察点辨认结果。

## 四个设计检查

**删除测试。** 假设删除这层包装：复杂度消失了，还是重新散落到多个调用者？前者可能是不必要的间接层；后者表明它在集中知识。但权限隔离、稳定兼容或生命周期边界也可能是必要价值，不能只按转发行数删除。

**变化局部性。** 一条业务规则改变，需要改几类承担不同职责的对象？若相同判断散在多个调用者，考虑把规则交回所有者；跨多个文件但各司其职不自动是坏设计。

**调用负担。** 调用者是否必须了解内部存储、锁顺序或重试协议？能否将这种知识收回模块，同时保留必要业务选择？小接口应减少必须记住的事实，不是压缩参数名。

**可观察性。** 是否能通过稳定接口判断行为？若测试只能探入私有对象，先辨认观察点选错还是接口遗漏了必要结果；不要为测试方便公开无业务意义的内部状态。

## 依赖与副作用

需要变化、隔离真实外部副作用或满足测试/安全边界时，可在合适位置传入依赖、提供适配器或控制时间/随机源。只有一个实现不自动禁止边界；同样，有两段类似代码也不自动需要框架。

能纯计算的核心尽量返回结果，外部操作集中在清楚边界；但领域真实需要副作用时应明确表达，不把“纯函数”变成拆碎所有流程的理由。

## 对照例子

差：三个调用方都依次检查余额、减余额、写记录、处理重复请求。看似各步骤都很小，但调用方承担一致性与重试知识。

较好：由拥有该事务语义的能力提供一次“执行扣减”的接口，明确重复请求与失败结果。内部可由多个小函数/适配器协作，不要求塞进一个大文件。

例外：跨服务无法共享事务时，不能用一个函数包装就宣称原子性；应明确部分成功、补偿和可观察状态，必要产品保证先回到语义取舍。

## 比较方案

只有当前边界存在真实不同承担方式时比较。看是否满足必需契约、调用复杂度是否减少、故障是否更清楚、变更是否更局部、过渡成本是否可承担。一个明显更简单且足够的方案就可结束，不固定并行 Agent 或方案数量。
