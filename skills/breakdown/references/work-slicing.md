# 工作切片：先辨认承诺性质

## 选择拆法

| 工作性质 | 合适单元 | 不应强求 |
| --- | --- | --- |
| 新增或改变行为 | 从稳定入口可观察的窄行为切片 | 每次都同时修改 schema、API、UI |
| 重要未决选择 | 可回答并会改变路线的决策/调查 | 把所有可查事实都开 Issue |
| 内部准备 | 明确启用后续工作的结构或工具变化 | 冒充用户完整功能已交付 |
| 跨代码库机械重构或迁移 | 可兼容的扩展、迁移批次、收缩 | 强切成无法保持兼容的“端到端”片段 |
| 多方共同修改一个契约 | 契约稳定化、受控分工、统一集成 | 各分支绿色即全局通过 |

## 行为切片

从一条可观察路径开始：输入/事件、必要状态、结果和最低验证。下一切片由剩余承诺与前一切片发现决定，不先堆完所有技术层。

例：任务超时可分为进入终态、拒绝迟到结果、状态重启后仍保留。范围仍由完整当前承诺约束，完成第一片不能删掉后两片。

粒度应让一次工作有清楚的改动与交接，而不是固定 token、行数、工时或目录数。若一个内部准备项没有独立安排、风险或验收价值，就作为实现步骤，不另开 Issue。

## 大范围重构：expand–contract

适用前提是一次机械变化会同时破坏大量真实调用者，且直接切换不能安全独立落地。不是所有重命名都需要兼容层。

1. 扩展：在现有契约允许范围内引入新形式，明确新旧读取、写入和转换规则；不要默认双写。
2. 迁移：按真实依赖与影响范围分批改调用者或数据。每批保留可工作的系统，并说明验证边界。
3. 收缩：确认所有支持范围内的调用者与数据已迁移，删除过渡路径。退出条件要可判断，不能“以后再清理”。

如果批次无法单独保持正确，使用已有集成分支/统一候选，明确只有最终集成承诺绿色；中间批次不冒充可发布成果。必须保留不被覆盖的用户改动。

例：公开字段改名有旧客户端，先接受两种输入并规定冲突优先级，按支持窗口迁移，再删除旧输入。若只有一个仓内私有调用点，直接原子改名和回归更简单，不创建临时兼容协议。

## 依赖与验收

依赖写“缺少什么结果、阻塞哪一步、什么事实解除”。最终验证须针对用户承诺与跨切片交互，不只是每项文件修改完成。

父子关系不代表顺序；优先级不代表技术依赖；“有相同 reviewer”也不自动要求串行。共享写入冲突可以通过限定边界或顺序消解。
