# 全景产品规划：目标、组成与承载

## 先恢复目标，不从已有代码反推产品

提取当前有效的使用者、结果、主要能力、边界与已知未知。区分确认的 Deferred 和尚未确认的方向；不把未来所有想法都当成承诺，也不把当前已实现部分当成完整目标。

已有地图可用则复用。工作图既保存交付安排，也保持已确认能力的可见性；远期节点可以粗，不需要现在可执行。

## 建立双向映射

对主要结果依次问：

1. 使用者或上游系统通过什么正式入口完成什么操作？
2. 哪些可辨认的组件、接口或材料共同承担它？不只列“质量能力”等抽象名词。
3. 哪个已有或必要工作项承载这组变化？工作项不是每个文件和函数。
4. 当前阶段完成到哪里，凭什么判断该阶段结果成立？
5. 哪些确认能力留到以后、由什么承载；哪些未知仍待决定？

反向检查每个主要工作项：它服务哪个目标、必要前置或可信风险？找不到依据时标为待确认，而不是为了凑覆盖保留。

这些映射可以是会话中的紧凑表格或已有 Issue 的必要内容，不要求新建覆盖数据库。

## 完整性与分辨率

上层检查能力范围与主要关系，近期检查输入、输出、依赖和完成条件；远期不提前选择类名、表字段或详细实施顺序。不能因为实现细节尚未确定就连主要交付组成也不说明。

候选技术不是确认需求。某组件是否必要仍未知时明确其待决问题和影响，不用“完整规划”替用户作产品选择。

## 决策工作与实施工作

“是否由本产品接管运行时”是决策；“实现已确认的运行记录接口”是实施。决策依赖解除后才细化受影响实施，不让两者混在一个模糊的开发事项里。

能精确提出的问题可以有决策承载，即使暂时被阻塞；还不能清楚描述的领域保留粗粒度未知，不强切成十个猜测任务。普通可查事实也不必全部生成 Issue。

## 阶段结果

阶段用有意义的完成状态区分，而非“又实现了三个功能”。当前阶段可小，但应能说明完成哪层承诺、启用什么后续工作，并保持完整目标的其他部分可见。

例：目标“单 Skill 可独立复制”对应完整 Skill 目录、导出入口、资源解析和消费端读取，而不是一个“改善打包”的抽象节点。当前只做独立导出时，不能把宿主自动安装也宣称完成。

反例：为体现全景预建半年后的数据库迁移、按钮、测试文件等数百任务。应上提为确认能力，临近实施再拆。

## 完成

主要确认目标有具体承担、当前阶段边界明确、近期下一步可接手、重要依赖与未知可见即可停止。动态工作留在既有 tracker，长期行为留在 Spec；不另建 ROADMAP/tasks 权威副本。
