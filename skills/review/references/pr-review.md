# PR 审查：固定候选与交付语义

1. 读取 PR 当前 head、base、比较范围和请求；辨认是否审查整个候选还是仅新增变化。审查中有更新时记录新旧身份。
2. 直接读原始描述、diff、适用约定和检查结果；作者摘要与旧 review 仅作定位。
3. 核对当前范围，有无意外文件、生成物漂移、秘密信息或不相关扩展；差异大小本身不是缺陷。
4. 分开判断要求是否实现、工程问题是否成立、证据是否适用。之前审过不免除受新变化影响的检查；没有影响的结论可继承。
5. 审查必要代码与契约，不把 PR 审查缩成只查状态；也不机械重做全部已有分析。新增疑点先检查可达条件与保护再报告。
6. 核对目标分支、冲突、项目必要检查与关闭语义。需要合并后验证的事项，不应随 PR 自动关闭；审查通过不是合并授权。
7. 报告候选、实质问题、建议、未检查范围与合并判断的边界。获准评论才写回共享对象。

## 变化与证据

head 更新后评估哪些结论失效，只复查受影响内容。基线与候选无法固定时，不批准未知对象。检查缺失是证据限制，不自动证明代码错误；核心风险未被覆盖且影响当前合并条件时明确阻断原因。

## 独立性

审查应直接检查候选和依据，不只复述实施者结论。一个清晰的小改动不强制两名 reviewer；高风险按项目规则使用独立判断，但不能让实施者换个名字声称独立审查。

GitHub 是否允许某账号提交 APPROVE 是平台权限事实，不改变静态判断内容；不能绕过保护或用自评伪装他人批准。
