# 实现审查：要求与工程质量

## 固定范围并追踪关键路径

从实际 diff、修改符号与相关测试出发，沿调用者、数据流、持久化和外部边界追踪。必要时读未修改代码以理解保护，不把探索扩大成全仓风格检查。

## 要求忠实度

将当前承诺映射到实现入口：缺了什么、部分实现什么、行为是否正确、是否新增未被要求的承诺。检查测试是否在真正错误时失败，不把有测试文件等同于行为覆盖。

明确工作切片与长期目标：本次无需实现整个产品，但不能漏掉当前已承诺部分。

## 工程质量

按实际变化选择检查：

- 状态与所有权：谁能改变对象，终态、不变量和责任是否被绕过？
- 数据与错误：部分成功、重试、资源释放、事务与错误传播是否正确？
- 边界与安全：输入、权限、敏感信息、外部返回和依赖是否按可信边界处理？
- 兼容与交互：支持中的调用者、协议、顺序、取消与并发是否仍成立？
- 维护与性能：规则是否散落、类型是否含糊、抽象是否有价值，是否引入真实可达的无界操作或热点负担？

格式和确定性静态检查优先交给工具；读者偏好不是规范违反。不因技术清单存在就机械逐项要求新测试或新文档。

## 结构问题的修复手法

| 现象 | 先确认 | 可考虑的修复 |
| --- | --- | --- |
| 多个调用者重复同一业务规则 | 是否真的共享变化原因与不变量 | 将规则交回所有者 |
| 调用者必须知道许多内部步骤 | 这些知识是否属于它的责任 | 收拢编排、缩小接口负担 |
| 同样条件反复出现 | 是否缺少明确模型，而非合理局部分支 | 明确类型、共享判断或统一分派 |
| 大量静默 fallback | 是真实兼容策略还是隐藏错误 | 明确失败结果与边界 |
| 新包装只转发参数 | 是否承担权限、生命周期或兼容 | 没有价值才考虑删除 |

这些是候选修复，不是模式匹配后强制重构。改动要消除复杂度，不只是把它移到更多文件。

## 形成结论前

按 Finding 校准方法检查真实触发条件和已有保护；区分本次回归、相关既有问题和无关旧债。两类审查视角可在一次阅读完成，不固定多 Agent。

例：要求实现取消，代码规范且测试绿色，但测试只覆盖正常完成，取消请求实际上被忽略。它是要求未落实，不能被代码风格良好抵消。
