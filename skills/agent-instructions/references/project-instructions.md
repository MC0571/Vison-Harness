# 把项目差异写成可执行指引

## 哪些内容值得长期保留

保留稳定的工作约定、权威入口、正确命令来源、安全和提交边界、真正局部差异。一次实施进度、临时分支、当次故障处理过程与个人偏好通常留在工作载体，不变成所有未来任务的约束。

已有信息可准确引用时不再复制。代码结构快照和每个文件列表容易失效，除非它们本身是稳定契约，否则只提供找到相关事实的方法。

## 规则的最小表达

> 在什么条件/范围下 → 执行什么动作 → 保留什么边界/例外 → 什么结果足够。

不要求四个固定标题，要求读者能辨认这四件事。

差：“所有工作都要遵循最佳实践并充分测试。”

较好：“修改公开错误语义时，核对受支持调用者与对应契约测试；内部重构且契约未变，不新建 Spec。命令从当前 CI/测试配置读取，环境未就绪时报告受阻而非通过。”

差：“每次工作前读完所有文档。”

较好：“改动数据所有权前读取相关架构约定；普通局部缺陷先读直接行为与调用链，出现跨边界影响再扩展。”

## 层级与冲突

根文件保存全仓稳定约定；局部只写适用范围内的真实差异。没有差异不新增。局部命令可以不同，安全约束不能因层级更近而未经授权放宽。

比较两条规则的对象、范围、优先级和有效决定。一般规则与合法局部例外不算矛盾；同一场景无法同时遵守时才需要澄清或修订。

## 质量检查

规则是否产生明确动作？是否可以误解为每次执行全部流程？是否重复了工具已经保证的事情？是否把有条件建议写成无条件门禁？是否为本次方便而降低已有约束？

每项新增规则应有实际项目需要，且具备停止条件。没有净收益可删除建议或零修改，不用指令行数表示完善程度。

## 接入宿主

核对真实宿主、工作目录、查找范围、优先级与覆盖机制；修改后从相关目录检查可发现与读取的路径。不要把路径存在当作已自动加载，也不要默认已有会话已刷新指令。

没有宿主验证能力时清楚报告文件与引用完成、自动加载未确认；不伪造配置字段。
