# 发布、部分成功与关闭

## 先按交付类型选择深度

包/构件发布关注版本、目标、内容一致性、依赖、许可证与消费者获取入口；PR 合并不自动需要生产发布检查。有运行影响的部署再处理健康、数据切换、渐进推进和恢复。

使用项目真实发布入口与支持环境，不从文档示例猜命令。版本已存在时核对是否为同一候选和构件：等价已完成可零写入；不一致时停下解释，不能覆盖后宣称幂等。

## 发布前的关键决定

对本次真实风险辨认：

- 发布哪一个不可混淆的候选/构件，目标环境是什么？
- 使用者通过什么路径验证结果，哪些旧调用者/数据仍受支持？
- 什么信号允许继续，什么信号要求暂停，什么情况需要恢复？
- 既定恢复动作是否在本轮授权内，谁承担超出当前会话的观察？

普通包发布可很简短；高影响部署需要更清楚的判断。不固定 feature flag、canary 百分比、时间窗口、错误预算数字或监控平台。

## 推进与观察

按已有部署机制选择一次性、分批或受控启用。需要分阶段时每阶段用项目相关信号决定继续/暂停，而不是时间一到自动扩大。

进程健康、错误/延迟、数据一致性和核心操作各说明不同事情。HTTP 200 或上传成功不必然证明用户路径可用；同时，无运行服务的库发布也不必创建健康端点。

长时间观察超出本轮执行能力时，明确已完成动作、尚未观察的区间和交接责任，不承诺在后台继续监控或把等待结果写成通过。

## 部分成功的处理

| 实际状态 | 首先核对 | 本轮内可能的动作 |
| --- | --- | --- |
| 构件已上传，Release 未确认 | 版本、摘要、Release 是否已生成 | 保留构件；原授权内只补缺失对象 |
| 请求超时但服务器可能成功 | 查询对象与目标状态 | 已成功则停止重复；未知则保持限制 |
| 代码切换，迁移中断 | 新旧版本可读写哪些数据、已完成批次 | 暂停扩大影响，选安全续跑或恢复 |
| 部署完成，健康/关键路径失败 | 是真实回归、设置还是依赖故障 | 按已授权预案暂停、回退或向前修复 |
| 合并成功，后置检查受阻 | 目标分支实际提交与检查缺口 | 如实报告；不自动关闭需验证的工作 |

每次恢复前确认当前状态，保留原失败和成功产物。不能直接从头重试、覆盖发布版本或用“全失败”抹去已产生副作用。

## 回退不只等于回退代码

新版本可能已经写出旧版本不能理解的数据、发送不可撤回的消息或改变外部状态。恢复方案应区分代码回退、配置关闭、补偿、数据恢复和向前修复；不因有旧 tag 就声称可完整回滚。

选择最小安全动作并核对授权。若无法安全回退，停止进一步扩散并说明所需决定；不能为了快速恢复而丢数据、绕过保护或未经授权改变生产。

恢复后按实际影响确认关键状态，不能把恢复命令退出成功等同于已经恢复。

## 关闭与结束

仅当对应承诺、必要后置条件和关闭授权都满足时关闭相应事项。当前切片完成不是上层能力完成，长期能力未完成也不阻塞合格当前版本。

PR 需合并后回读/验证时使用普通关联，防止自动关闭。构建、上传、tag、Release、部署、观察和关闭分别报告；只对本轮承诺的层级作完成声明。
