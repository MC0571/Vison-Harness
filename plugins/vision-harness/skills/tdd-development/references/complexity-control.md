# 复杂度控制

对新增抽象、兼容层、防御分支或流程要求逐项询问：它服务于哪项已确认需求、可信风险或明确维护需要？更简单的现有结构为什么不够？没有依据的负担不进入候选。

## 选择分支

- 已有模块、标准库、平台能力或已安装依赖能直接承载时复用，不创建平行机制。
- 重复不足以形成稳定模式时就近实现；真正跨职责时不能只为减少文件数而混在一起。
- 兼容只覆盖明确支持的调用方、数据或版本；不为假想迁移保留双写和永远分支。
- 防御重点放在外部输入、权限、数据完整性和可信故障保护；受控内部路径依赖已建立契约。
- 局部简化能解决问题时不升级为全局重构。没有可证明收益时允许零改动。

必要保护不能以“简单”为名删除：认证授权、边界输入校验、避免数据丢失的错误处理、可访问性和安全回滚条件都保留。

例：唯一调用点只需要固定映射时使用局部字典，不增加 Strategy/Factory。第三个具有相同变化规则的调用点出现，并且独立演进已造成修改遗漏时，再考虑抽取。

异常例：两个模块同时操作同一事务边界。把逻辑塞进一个文件虽然文件更少，却混淆数据所有权；应保留边界，并删除的是推测性适配层而不是职责。
