# 复杂度诊断与简化

读取[共同规则](../../references/shared-rules.md)。确定本次检查对象、有效承诺和操作权限；“看看是否过重”只授权分析，不等于允许删除文件、规则或代码。

## 从实际负担定位问题

检查重复概念与事实、推测性扩展、无兼容承诺的旧路径、重复边界检查、错误被隐藏、无必要的审批与全量重跑。用真实调用、变更记录或运行成本说明负担，不仅凭行数或个人风格判断。

对每项候选问：它保护哪项已确认需求、可信风险或维护需要？已有哪一层提供同样保证？删去后最坏的合理结果是什么？无法确认用途的内容先保留并说明缺口，不因为“目前没出过事”判定保护无用。

## 选择更简单的替代

优先删除无依据分支、复用已有权威规则、收缩抽象或减少重复检查。说明替代前后的行为、风险、调用者和维护代价。边界清楚的多个文件可能比一个大文件更简单，不为减少文件数合并无关职责。

流程简化明确什么触发、什么可以跳过、何时结束。不能为了让当前变更通过而降低审查标准，也不能因效率理由取消必要权限、数据保护或实际受影响的验证。

## 按授权落实

只建议时给出可操作的改动及保留理由，不自动建立一批治理 Issue。获准修改时，以小而可撤回的步骤实施，保留用户改动和重要历史；涉及行为变化先处理相应约定，纯重构不新增 Spec。

复用适用测试，补足删除路径造成的真实风险，并检查受影响调用者。不能用“更简洁”代替正确性；未运行的检查明确标注。远期能力有有效承诺时保留追踪，不因删去无效实现而取消目标。

返回已发现的复杂度、保留的必要保护、实际变化或零写入结论，以及可观察的收益与未知。没有值得改的内容时直接结束，不制造整改任务。
