# 从依赖分析到真实集成

## 方案模式

先写明共同承诺和输入版本。逐项辨认输出、允许修改范围、真正依赖与共享资源；父子关系、优先级和“看起来相关”不自动成为阻塞。

每条关键依赖回答：缺什么结果、阻塞开始/集成/验收/发布哪一步、用什么事实解除。依赖是阶段性的，例如实现可先开始，最终发布仍等待迁移。

比较串行与并行：接口稳定、修改边界可分、交接成本低时并行；共享 schema 或责任未定时先串行收敛契约。不要为了启动更多 Agent 而制造拆分。

方案至少说明共同契约、各自输出、交接条件、共享修改策略、集成责任、统一候选验证和失败时的局部调整。只要求方案时不启动执行者或修改代码。

## 执行模式

1. 固定基线、目标分支、候选、已有工作区改动与本轮权限。隔离可以用宿主 worktree；不能清理或覆盖未知改动。
2. 将范围、准确输入、输出、允许副作用与停止位置交给真实执行者。宿主无委派时按同一安排串行推进，不建设调度器。
3. 交接检查实际提交/diff、文件列表、构件、命令结果与未决问题。摘要仅作导航；出界修改先隔离并解释，不直接覆盖。
4. 接口或依赖改变时找出受影响调用者与交接，局部调整，不重做全部计划。旧结果仍适用则保留。
5. 应用变化前确认候选身份、冲突和目标。解决文本冲突后核对两侧意图、共同契约和数据语义；不要把“能合并”当成正确集成。
6. 在一个明确候选上连接真实使用路径，检查共享状态、错误传播、兼容和迁移；运行与本次承诺相称的集成与回归。
7. 报告已集成内容、准确候选、证据和剩余限制；到本轮未授权的提交、推送、PR、合并或发布边界停止。

## 失败与重排

一个分支失败不自动让所有工作停下。保留已经成立的结果，只重排依赖失败产物的部分。一个执行者越界修改共同文件时，核对原契约与原因，按意图重分边界；不默认丢弃任意一方改动。

没有单独安装的实施 Skill 时，协调仍要承担获准结果，可以使用现有宿主完成实现与必要测试；不能把核心责任改写成“请安装另一个 Skill”。

## 示例

暂停能力涉及执行端、调用端和取消语义。先确认暂停状态与接口，再并行实现调用端与执行端。统一候选上检验“暂停后取消”和“取消后到达暂停结果”，不能只相加两个分支的测试结论。

另一例：共享 schema 必须先决定；只解除已稳定接口的实现阻塞，保留迁移对发布的约束。

## 完成

方案可执行即可完成方案请求；执行请求必须有真实交接、统一候选与必要验证，或准确说明被阻塞/失败的部分。不得把前者当成后者。
