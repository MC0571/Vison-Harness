# 行为规格制定与演进

先读取[共同规则](../../references/shared-rules.md)和[行为、架构与审查规则](../../references/engineering-rules.md#7-按变化维护-spec架构和决策)。从当前 Issue 和有效决定取得范围，而不是从现有代码或已写测试反推承诺。只获准分析时返回方案，不修改规格。

## 确定受影响的语义边界

沿真实使用场景检查可观察行为、状态转换、领域数据、接口、权限、安全、失败、兼容和必要非功能保证。定位已有 Spec、Schema、Contract 和架构约束；区分必须成立的性质与当前实现方式。

将变化归为新增、局部修订、已有约定足够或无需语义变化。纯重构且约定未变时明确不修改 Spec。只有独立验证、复用或演进价值的边界才拆文件，沿项目已有语义目录，不用任务序号建立平行规格。

## 写出可判断的行为

定义关键术语、参与者、前提、正常结果、失败结果和不变量。状态行为说明允许与禁止的转换、终止状态、重复或迟到输入；接口行为说明输入输出、错误语义及兼容承诺。并非每项都需要独立章节，只覆盖本次相关边界。

每项重要要求应能通过场景、断言或观察区分满足与违反。至少思考一个成功路径和一个最可能破坏承诺的反例。把未决产品取舍保留为未决，不用技术选择替用户回答；只暂停受其影响的约定。

与相邻规格核对术语、所有权、状态、错误和权限是否冲突。引用已有共同约定，不复制两份权威规则；实现细节留给设计或代码。Spec 不保存负责人、里程碑、进度或接受日期。

## 保存与交接

获准后完整读取目标文件，作最小语义修改，保留无关规则并回读。说明行为差异、受影响调用者和现有保证，不为让实现通过而降低约定。

重要或高风险规格在依赖它的大量实施前交给 spec-review，提供准确候选、范围和待决问题；不把自检命名为独立接受。项目不要求额外审查且约定已充分时，按授权进入设计或实施，不强制增加审批。

返回采用的语义依据、实际修改或无需修改的理由、未决部分与实施注意事项。规格写成不等于行为已实现。
