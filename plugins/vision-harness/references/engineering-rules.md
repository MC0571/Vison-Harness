# Engineering Rules

This runtime reference is generated from the repository's accepted method and behavior sources. It is intentionally self-contained; edit the source documents and rerun the assembly instead of hand-editing this file.

## 4. 维护依赖，并设计有效的推进方式

工作关系图不仅要说明归属，还要帮助项目高效推进。

需要区分：

- 父子关系：表示工作归属，不自动表示执行顺序；
- 优先级：表示投入顺序，不自动构成技术依赖；
- 真实依赖：缺少另一项结果时，当前工作某个阶段确实不能继续；
- 修改冲突：业务上可以并行，但会同时修改共享接口、文件或资源，需要协调。

对重要依赖，应能够说明：

- 缺少什么结果；
- 它阻塞的是开始、实现、集成、验收还是发布；
- 什么事实出现后可以解除；
- 在解除之前，还有哪些工作可以先做。

**依赖只阻塞它实际影响的阶段。** 尚不能集成，不代表不能调查、准备测试或完成独立工作；无关的远期依赖不能阻塞当前交付。

在投入大量设计和实现之前，优先验证那些一旦不成立就会改变方案选择、职责边界或交付路线的关键假设。

但不能把“尚未适配”直接解释为“路线不可行”。应区分：

- 正常实现成本；
- 可以接受但需要决策的代价或限制；
- 会破坏已经确认产品边界或关键约束的根本问题。

并行方案不能只说“同时启动几个 Agent”。它还应说明：

- 并行工作的共同依据；
- 每项工作的明确输出和允许修改的范围；
- 共享接口或资源；
- 集成责任和顺序；
- 集成后需要重新验证的行为。

如果协调和冲突成本高于收益，应减少并行或改为串行。

推进策略在关键假设、接口、阻塞条件或集成风险发生变化时可以重新调整。

Skill 协作按触发条件组织：说明交出的范围、来源/版本、允许副作用、缺口和预期结果；接收方只复核自身动作所需依据。交接不扩大授权，不隐藏失败，不要求专用交接状态文件。架构调整只暂停真正受影响的实施，不自动阻塞其他已具备条件的工作。

## 7. 按变化维护 Spec、架构和决策

Issue 是工作生命周期容器，主要说明为什么存在、整体位置、本次范围、边界、依赖、暂缓内容和关闭条件。

Spec 不负责项目进度和工作排序。Spec 精确定义系统必须满足的长期行为和约束。

范围决策属于工作规划；Spec 定义该范围涉及的长期系统规则。测试证明实现是否满足这些规则，但不能反过来决定本次应该交付什么。

### 约定不是流程的另一份改写

对 Vision Harness 自身，架构定义具体产品组成与条件协作；必要 Spec 或共享规则提供独立于当前实现的正确性依据；SKILL.md 和运行参考描述怎样完成工作；行为评估据此检查实际结果。没有独立 Spec 文件不等于没有长期约定，Skill 指令也不能成为自己验收的唯一依据。

相同要求在契约、实现和测试中有对应，不属于无效重复；三份材料都大段复述相同操作步骤才是问题。某些可观察顺序本身是约束，例如先确认授权再写入、先得到回答再作依赖该回答的决定，应保留。内部策略、文档措辞和合理的实现差异无需锁定。

不按二十个候选职责生成二十份 Spec，也不先写完 Skill 再从它倒推预期结果。定义近期责任时同步明确必要行为与正反场景，已有共享约定优先引用。

### Spec 不是固定的一份文件

一次变化可能触碰：

| 变化 | 常见规格对象 |
| --- | --- |
| 用户或系统行为 | 行为规格 |
| 状态和生命周期 | 状态模型 |
| 长期领域数据规则 | 领域数据语义 |
| API / 事件 / 协议 | 机器可读契约 |
| 权限规则 | 权限规格 |
| 安全保证 | 安全规格 |
| 兼容要求 | 兼容性规格 |
| 必须满足的性能、可用性等性质 | 非功能要求 |

执行时先问：当前范围改变了哪些长期保证？

Spec 是否完整，不看文件套餐是否齐全，而看当前范围中需要长期保证的行为和约束，是否都有明确、唯一、可验证的表达。

只有具有独立验证、复用或演进价值的内容，才值得拆成独立规格对象。

Spec 目录按稳定的领域、能力或契约边界使用语义名称，不使用 Issue 编号、创建顺序或临时阶段作为身份。

Spec 文件不承担负责人、Milestone、任务进度等工作流信息。只有系统行为或约束变化时，Spec 才应改动。

### 架构、ADR 和技术方案

**架构**记录系统长期如何组织，例如子系统边界、依赖方向、数据归属、跨组件协议、信任边界、扩展点和部署关系。

**ADR**记录一个会长期约束未来工作的重大决定为什么这样做。只有存在真实备选方案、明显权衡、较高修改成本并会影响后续工作时，才值得记录。

**技术方案**只服务一次具体变化，说明如何安全实施，例如受影响组件、变更顺序、迁移、兼容、测试、回滚和风险，默认留在 GitHub。

进入实现前，Agent 判断当前变化是否改变长期架构。如果只是沿用现有架构实现一个功能，可以直接继续；如果改变长期边界、依赖、数据归属、协议、一致性、信任边界、部署拓扑或扩展方式，再进入架构设计，必要时形成 ADR。

## 9. 按对象组织审查，而不是机械增加审查轮次

实施者自检、自动测试、独立审查和最终验收是不同判断。

必要时，审查应由能够独立形成判断的 reviewer 完成：直接读取当前候选变更、相关规则和证据，而不是只复述实施者的完成摘要。

但并不是所有工作都需要多人、多模型或多 Agent。审查强度应与风险、影响和项目规则相称。

三类常见审查对象是：

### Spec 审查

关注：

- 当前承诺是否被准确表达；
- 行为、边界、异常和约束是否清楚；
- 是否存在冲突、遗漏或不可验证要求；
- 是否擅自扩大或缩小范围。

Spec 合理不能证明代码已经实现。

### 代码审查

关注：

- 实现是否正确；
- 是否满足相关 Spec 和项目约定；
- 是否破坏架构；
- 是否引入没有依据的复杂度；
- 测试是否真正覆盖风险。

代码看起来正确不能证明正式交付路径已经验证。

### PR 审查

关注当前候选变更是否具备本次合并或交付所需的：

- 范围；
- 证据；
- 必要审查；
- 授权；
- 受影响检查结果。

PR 审查不机械重做前面全部工作，而是确认这些结论是否仍适用于当前候选版本。

审查通过不能自动产生合并、发布或关闭上层长期能力的授权。

修复后的重验只扩大到受影响范围；没有依据时不要求重新执行所有昂贵验证。
