## 3. 保留完整目标，但明确本次交付

编程 Agent 很容易把当前可见任务当成整个产品。Vision Harness 要求主要目标和能力保持可见，但不要求提前确定所有远期实现细节。

高层规划先保证主要能力不遗漏：

- 已确认属于最终目标的能力不能因为暂时不做而消失；
- 已确认目标、待验证假设和未知问题要分开；
- 远期工作保持粗粒度；
- 近期工作才逐步细化到可实施和可验证的程度。

当前范围可以小，但不能被偷偷改写成完整产品。

同样，完整产品还有远期内容，也不能自动阻止一个范围明确、真实可用的当前交付。

需要区分不同层级的“完成”：

| 工作对象 | 完成意味着什么 |
| --- | --- |
| 探索任务 | 已获得足以支持当前决定的证据 |
| Spec 或架构工作 | 相应规则已经按项目约定完成审查或接受 |
| 实施切片 | 本切片承诺的行为和验证已经满足 |
| 当前版本 | 本版约定范围能够通过正式入口获得并满足放行条件 |
| 长期能力 | 当前有效的完整能力承诺已经满足 |

这些完成结论不能互相替代。

把剩余内容转移到其他 Issue，可以解决“不遗忘”，但不能自动证明原 Issue 已经完成。范围变更需要有相应授权和依据。

暂缓、冻结、不采用、被替代也不是同一个含义。停止一条实现路线时，还要判断它承担的有效目标是否需要由其他工作承接。

### 单项工作整理

单个 Issue、缺陷、调查或重构请求不需要重新做全景规划，但必须形成可接手的承诺。先沿现有愿景和父级工作确认它为什么存在，再辨认本项类型、当前范围、明确边界、关联行为约定、完成条件和仍未决问题。

功能工作说明可观察结果；调查工作说明要回答的问题和停止条件；重构说明必须保持的行为；缺陷区分预期与实际表现。已有清楚工作直接复用，不为调用方法而重写正文。

完成条件覆盖当前承诺，不能只写“测试通过”或“子项全部关闭”。若所有下层工作完成后，上层仍可能缺正式入口、集成、持久化、兼容或交付结果，应在当前承诺中补出缺口，而不是暗中缩小原目标。

只有需要独立安排、协作或验收的结果才值得成为子 Issue；普通编码步骤留给实施。父子归属、优先级、技术依赖和共享修改冲突分别表达。已有能力容器能承接暂缓工作时直接复用，不为每个细节新建事项。

### 从目标到具体产品交付

高层规划不能只覆盖抽象能力。它需要连接 Vision、阶段目标、结果证据、具体产品组成 / 交付物、Milestone、FR / Issue 与下一交付批次，使用户能判断阶段价值，后续 Agent 能直接接手。

规划可借鉴 OKR 的结果导向，但不建立新的 OKR 文件、状态库或固定编号体系。阶段目标描述希望达成的状态；结果证据说明怎样知道目标取得进展或达成，而不是任务清单。

目标、产品组成和实施工作不能互相替代：

- 只有抽象目标，没有具体交付物，规划不够具体；
- 只有 Skill、Hook 或文件清单，没有用户或上游系统结果，不能证明目标成立；
- 一个 FR 可以由多个组件实现，一个组件也可以服务多个 FR；
- FR、Milestone、Skill 和结果证据不要求一一对应。

规划完成前应做反向闭合检查：

1. 如果所有子 Issue 都完成，上层承诺是否仍可能明显没有实现？
2. 用户能否看懂实际交付物？
3. 后续 Agent 是否无需重新做产品拆解即可继续？
4. 当前 Milestone 是否说明用户或上游系统能获得什么，并有相应验证方式？

滚动细化时，完整产品层尽可能保持主要目标和主要产品组成可见；当前 Milestone 明确实际交付、结果证据和关键依赖；下一交付批次细化到可进入 Spec、设计或实施；更远工作保持粗粒度。新事实出现后只修订受影响部分，不从头重建规划。

规划审查不能只依赖 Issue 数量、Milestone 是否已创建、Parent / Sub-issue 关系是否正确或字段是否填全。这些只能证明配置，不能证明产品规划可用。

## 4. 维护依赖，并设计有效的推进方式

工作关系图不仅要说明归属，还要帮助项目高效推进。

需要区分：

- 父子关系：表示工作归属，不自动表示执行顺序；
- 优先级：表示投入顺序，不自动构成技术依赖；
- 真实依赖：缺少另一项结果时，当前工作某个阶段确实不能继续；
- 修改冲突：业务上可以并行，但会同时修改共享接口、文件或资源，需要协调。

对重要依赖，应能够说明：

- 缺少什么结果；
- 它阻塞的是开始、实现、集成、验收还是发布；
- 什么事实出现后可以解除；
- 在解除之前，还有哪些工作可以先做。

**依赖只阻塞它实际影响的阶段。** 尚不能集成，不代表不能调查、准备测试或完成独立工作；无关的远期依赖不能阻塞当前交付。

### 关键假设的有界验证

在投入大量设计和实现之前，优先验证那些一旦不成立就会改变方案选择、职责边界或交付路线的关键假设。先检查已有权威文档、实际配置、历史运行记录和当前适用证据；这些事实已经足够回答问题时直接使用，不为了“更确定”制造新试验。

需要进一步调查时，先把未知改写成可回答的问题：当前哪个决定依赖它、如果不成立会改变什么、哪些工作真正受影响。优先采用成本最低且能回答问题的资料核对；只有现有证据不足时才进入实际 probe 或试验。

实际试验必须在看到结果之前明确：

- 输入、只改变的必要变量和预期观察量；
- 环境、版本、数据范围和允许副作用；
- 有限预算，例如尝试次数、时间、样本或资源上限；
- 停止条件：问题已回答、预算耗尽、环境无法满足或继续试验不再增加决策信息；
- 判断判据：什么结果支持继续原路线，什么结果要求调整，什么结果只能判为仍不确定。

判据应先于结果形成，不能看到不喜欢的结果后再移动标准。试验优先使用获准的隔离环境和非敏感数据；不能为了得到答案擅自访问生产资源、付费服务、真实账号或提升权限。

记录失败与环境错误，并把它们与产品事实分开。权限不足、网络故障、工具不支持、夹具错误或环境未就绪，只能说明本次试验没有取得相应产品证据，**不等于产品路线不可行**。模拟或替身只支持其模型范围内的结论，不能冒充真实安装、协议或外部集成通过。

解释结果时分别列出直接观察、依赖这些观察的推断和剩余未知，并区分：

- 正常实现或适配成本；
- 可以接受但需要决定的限制或代价；
- 会破坏已确认产品边界、关键约束或路线前提的根本问题。

问题已回答或达到预算就停止。结论只阻塞或改变实际依赖该假设的工作；其他已具备条件的工作继续。停止一条实现路线时，仍需说明它承接的有效目标由什么工作继续承担。

### 并行与执行期协调

并行方案不能只说“同时启动几个 Agent”。它还应说明：

- 并行工作的共同依据；
- 每项工作的明确输出和允许修改的范围；
- 共享接口或资源；
- 集成责任和顺序；
- 集成后需要重新验证的行为。

如果协调和冲突成本高于收益，应减少并行或改为串行。

协调请求首先区分两个停止位置：

- **只要协调方案**：形成依赖、分工、交接、集成与重验安排后结束，不启动实现或修改未获授权的对象；
- **已授权执行协调**：Breakdown 保持协调责任，不能在方案写完时结束；它持续到请求范围内的真实交接和统一候选整合完成，或遇到明确授权、依赖、工具或失败边界。

进入执行模式后：

1. 固定共同约定、输入版本、各项输出、修改边界、共享资源和集成责任；没有真实执行者时标记待分配，不虚构已委派。
2. 宿主支持且本轮允许委派时，向执行者传递准确范围、版本、权限和停止条件；不支持子 Agent 时按相同边界串行推进。单项代码实现仍由 TDD/实施方法承担，协调入口不把规划职责偷换成随意编码。
3. 每次交接直接检查实际 diff、构件、测试结果或项目记录，而不是只接受“已完成”摘要。共享事实写入前重读当前版本，防止不同执行者用旧快照互相覆盖。
4. 接口变化、阻塞解除、资源冲突、失败或新证据出现时，只重新安排受影响部分；保留仍成立的工作和证据，不重建全局计划。
5. 需要把多个结果组成统一候选时，以准确候选为对象完成必要集成。实现或语义修正按需交给 tdd-development；创建 PR、合并等候选操作只在相应授权存在时交给 release-delivery；组合后的证据缺口按需交给 change-verification。三者是条件协作，不是每次必经流水线。
6. 文本冲突解决后仍要检查接口、状态、兼容和共享语义。各分支分别通过不等于组合候选通过；在同一候选上重新执行受影响的集成验证。

执行期协调只有在本轮要求的真实结果已经完成交接、形成准确统一候选并取得必要的受影响验证，或遇到具体且已说明的停止边界时，才可以结束。不能把“协调方案已经可执行”冒充“获准的协调与集成已经完成”。

推进策略在关键假设、接口、阻塞条件或集成风险发生变化时可以重新调整。

方法协作按触发条件组织：说明交出的范围、来源/版本、允许副作用、缺口和预期结果；接收方只复核自身动作所需依据。交接不扩大授权，不隐藏失败，不要求专用交接状态文件。架构调整只暂停真正受影响的实施，不自动阻塞其他已具备条件的工作。
