# Shared Rules

This runtime reference is generated from the repository's accepted method and behavior sources. It is intentionally self-contained; edit the source documents and rerun the assembly instead of hand-editing this file.

## 1. 先确认本轮任务和授权

开始工作前，先确定用户这次要求的是什么，以及允许产生哪些副作用。

常见工作包括：

- 调查和分析；
- 提出方案；
- 修改愿景或 GitHub 规划；
- 编写或修改 Spec、架构和项目规则；
- 实施代码与测试；
- 审查和验收；
- 合并、发布或执行外部操作。

这些工作可以使用同一套项目事实，但授权范围不同。

**具备继续条件，不等于已经获得继续授权。**

例如，用户只要求“评估这个方向”，Agent 即使已经找到成熟方案，也不能因此自行创建实施 Issue、修改产品代码或发布结果。

反过来，用户已经明确授权“完成这个 Issue，提交到独立分支，不要合并”，Agent 应在这个范围内连续推进，不必每一步重新请求确认；到合并边界时停止。

不能仅凭 Issue 状态、Milestone、CI 通过、审查结论或“技术上可以继续”推导出新的授权。

Agent 应读取足以支撑当前决定的上下文，不需要每次重新阅读全部历史、所有 Spec 和全部规划。

## 3. 保留完整目标，但明确本次交付

编程 Agent 很容易把当前可见任务当成整个产品。Vision Harness 要求主要目标和能力保持可见，但不要求提前确定所有远期实现细节。

高层规划先保证主要能力不遗漏：

- 已确认属于最终目标的能力不能因为暂时不做而消失；
- 已确认目标、待验证假设和未知问题要分开；
- 远期工作保持粗粒度；
- 近期工作才逐步细化到可实施和可验证的程度。

当前范围可以小，但不能被偷偷改写成完整产品。

同样，完整产品还有远期内容，也不能自动阻止一个范围明确、真实可用的当前交付。

需要区分不同层级的“完成”：

| 工作对象 | 完成意味着什么 |
| --- | --- |
| 探索任务 | 已获得足以支持当前决定的证据 |
| Spec 或架构工作 | 相应规则已经按项目约定完成审查或接受 |
| 实施切片 | 本切片承诺的行为和验证已经满足 |
| 当前版本 | 本版约定范围能够通过正式入口获得并满足放行条件 |
| 长期能力 | 当前有效的完整能力承诺已经满足 |

这些完成结论不能互相替代。

把剩余内容转移到其他 Issue，可以解决“不遗忘”，但不能自动证明原 Issue 已经完成。范围变更需要有相应授权和依据。

暂缓、冻结、不采用、被替代也不是同一个含义。停止一条实现路线时，还要判断它承担的有效目标是否需要由其他工作承接。

### 从目标到具体产品交付

高层规划不能只覆盖抽象能力。它需要连接 Vision、阶段目标、结果证据、具体产品组成 / 交付物、Milestone、FR / Issue 与下一交付批次，使用户能判断阶段价值，后续 Agent 能直接接手。

规划可借鉴 OKR 的结果导向，但不建立新的 OKR 文件、状态库或固定编号体系。阶段目标描述希望达成的状态；结果证据说明怎样知道目标取得进展或达成，而不是任务清单。

目标、产品组成和实施工作不能互相替代：

- 只有抽象目标，没有具体交付物，规划不够具体；
- 只有 Skill、Hook 或文件清单，没有用户或上游系统结果，不能证明目标成立；
- 一个 FR 可以由多个组件实现，一个组件也可以服务多个 FR；
- FR、Milestone、Skill 和结果证据不要求一一对应。

规划完成前应做反向闭合检查：

1. 如果所有子 Issue 都完成，上层承诺是否仍可能明显没有实现？
2. 用户能否看懂实际交付物？
3. 后续 Agent 是否无需重新做产品拆解即可继续？
4. 当前 Milestone 是否说明用户或上游系统能获得什么，并有相应验证方式？

滚动细化时，完整产品层尽可能保持主要目标和主要产品组成可见；当前 Milestone 明确实际交付、结果证据和关键依赖；下一交付批次细化到可进入 Spec、设计或实施；更远工作保持粗粒度。新事实出现后只修订受影响部分，不从头重建规划。

规划审查不能只依赖 Issue 数量、Milestone 是否已创建、Parent / Sub-issue 关系是否正确或字段是否填全。这些只能证明配置，不能证明产品规划可用。

## 5. 正确读取和安全修改项目事实

Vision Harness 不建立自己的平行状态系统，而是读取并操作项目已有的权威事实。

常见分工是：

| 事实 | 常见维护位置 |
| --- | --- |
| 项目长期目标 | `VISION.md` 或项目已有权威入口 |
| 路线图、Milestone、优先级、负责人、工作状态 | GitHub |
| 能力、功能、暂缓工作、父子关系和依赖 | GitHub Issue |
| 长期系统行为和约束 | Spec |
| 当前长期架构 | 架构文档 |
| 重要长期设计决策的原因 | ADR |
| 一次变更的技术方案 | GitHub |
| 当前实现 | 代码 |
| 可执行保证 | 测试 / Schema / Contract |

**一种事实只维护一个权威来源，但不同事实不能被压缩成同一个“完成”状态。**

需要区分：

- 承诺：应该交付什么；
- 状态：工作目前处于什么阶段；
- 证据：特定对象在特定条件下证明了什么；
- 授权：谁允许执行哪些操作；
- 历史决定：过去发生了什么以及为什么。

发现描述不一致时，先比较它们是否针对同一个对象、版本、范围和时间，再判断是否真正冲突。

规划可以调整，但已经发生的重要实施、验收、取消、替代和决定记录不应仅为了让路线图更整洁而被抹掉。

Vision Harness 默认不要求创建与 GitHub 平行的 `ROADMAP.md`、`tasks.md` 或自己的 `state.yaml`。已有项目的纯导航、自动生成视图和明确非权威摘要可以保留，只要它们不成为第二份需要手工同步的事实来源。

### 修改共享事实时

Agent 在修改 Issue、PR、规则文件或其他共享事实前，应：

1. 读取当前完整内容和相关关系；
2. 确认本轮授权允许修改哪些部分；
3. 保留与本次修改无关的有效内容；
4. 在工具能力允许时检测读取后是否发生并发变化；
5. 写入后重新读取并核对实际结果；
6. 操作结果不明时先查询，不盲目重复创建或覆盖。

这些规则降低并发和重复操作风险，但不替代 GitHub 或具体工具提供的原子更新和权限控制。

## 6. 维护 Agent 工作约定和审查规则

仓库中的长期事实不仅包括产品行为和架构，也可以包括长期有效的 Agent 工作约定。

Vision Harness 应按需要帮助项目创建和维护 `AGENTS.md`：

- 根目录文件保存全仓适用的工作规则、事实入口、构建测试入口和关键边界；
- 子目录文件只保存该范围特有的差异；
- 没有局部差异，就不创建局部文件；
- 已经由 Spec、架构或其他权威文档维护的规则，应引用而不是复制。

维护不仅包括新增，也包括发现失效、重复、冲突和已经不适用的规则。

项目使用的宿主可能有不同的 `AGENTS.md` 查找、覆盖和加载方式。Vision Harness 应依据实际宿主验证适用规则是否真的能被 Agent 读取，而不能仅凭文件存在就宣布配置完成。

修改 `AGENTS.md`、Skill、审查规范或 Agent 配置，可能改变后续 Agent 行为，不能仅因为文件是 Markdown 或配置文件就自动视为无风险修改。

实施者不能为了让当前工作通过，未经授权先放宽约束自己的规则或审查标准。

### 审查规则

Vision Harness 应帮助项目在确有需要时建立长期审查规则，例如：

- Spec 审查：行为、边界、异常、约束和可验证性是否清楚；
- 代码审查：实现是否正确、是否满足相关约定、是否破坏架构、是否引入无必要复杂度；
- PR 审查：当前候选变更的范围、证据、审查和授权是否足以支持本次合并或交付判断。

这些是不同审查对象，不代表每次必须有三个文件、三名 reviewer 或三轮审批。

审查规范应说明：

- 何时触发；
- 需要读取哪些输入；
- 检查什么；
- 什么构成阻断；
- 什么只是建议；
- 审查者允许做什么。

没有发现问题可以是正常结果。风格偏好和可由 CI 自动处理的问题，不应为了体现审查工作量而被包装成阻断。

规则可以由项目文档、Vision Harness 的 Skill 或宿主支持的 Agent 配置承载。子 Agent 是一种执行方式，不是审查规范本身；一次审查结果仍应留在对应的 Issue、PR 或项目既有载体中。

## 8. 用 TDD 实施，同时抑制没有依据的复杂度

TDD 是实现方法，不负责发现完整范围。

外层由 Issue 的当前范围和相关 Spec 决定本次必须满足哪些行为；内层按行为切片执行“红灯 → 绿灯 → 重构”。

例如“给执行实例增加超时”可以拆成：

```text
切片 1：运行中的执行实例到期后进入“已超时”状态
切片 2：已超时的执行实例拒绝迟到的成功结果
切片 3：超时状态能够被正确持久化并重新读取
```

不要机械地按“数据库 → 服务 → API → 最后补测试”串行拆分。

每个切片中，只写使当前行为成立所需的实现。这里的“最小”针对实现，不代表可以缩小已经确认的完整目标。

重构阶段除了代码质量，还要检查：

- 是否符合既有架构；
- 是否产生重复概念或意外接口；
- 是否为了当前切片阻碍已知目标；
- 是否借未来需求之名提前实现暂缓工作；
- 是否出现没有实际依据的抽象、兼容路径或防御逻辑。

对于新增的复杂度，应能够回答：

> 这项复杂度服务于哪项已确认需求、可信风险或明确维护需要？更简单的方案为什么不够？

仅凭“以后可能用到”“生产级系统都应该有”不能自动成立。

这不意味着删除必要的权限校验、输入验证、数据保护、错误处理、超时、恢复和真实质量保证。简化不能成为降低已有承诺的理由。

流程本身也受同样规则约束。新增检查、文档或审批应能说明防范的风险、触发条件和结束条件。

## 10. 用适用证据判断完成和交付

“有证据”不等于“这个证据能支持任何结论”。

验收结论必须受证据的以下范围约束：

- 对应对象或构件；
- 代码或文档版本；
- 运行环境；
- 实际使用路径；
- 行为覆盖范围；
- 证据是本轮直接执行、合理继承，还是对已有结果的审计。

例如：

- 单元测试通过，证明对应内部行为；
- Contract 验证通过，证明相应接口契约；
- 正式安装成功，证明安装路径；
- 真实 Agent 从正式入口完成任务，才能支持相应真实使用路径结论。

这些结论不能互相替代。

旧证据可以复用，但必须能够说明当前变化没有影响它支持的结论。受影响的部分重新验证；无关部分不为了“更完整”全部重跑。

一次工作结束时，还要判断完成的是哪一层承诺，不能只说“Done”。

同样，条件已经满足时应该允许继续和交付：

- 远期能力未完成，不自动阻塞本版；
- 无关文档缺失，不阻塞当前工作；
- 非相关未知尚未解决，不阻塞已有明确约束下的实现；
- 没有新事实时，不应继续生成治理改动。

## 11. 根据新事实继续、调整或停止

Vision Harness 不是一条从愿景只向代码前进的流水线。

项目应持续检查：

- GitHub 中的工作是否仍覆盖当前有效愿景；
- 代码是否仍符合架构；
- 不同 Spec 是否冲突或重复；
- 暂缓工作是否仍然有效；
- 当前依赖和推进策略是否仍然合理；
- 当前路线是否仍有证据支持。

新证据出现后，可以：

- 继续原方案；
- 调整范围或顺序；
- 替换实现路线；
- 冻结暂不处理的路线；
- 明确不再采用某种方案；
- 在获得相应授权后修改当前目标或边界。

停止某条实现路线，不代表它承担的有效产品目标自动消失。仍然有效的需求需要明确由什么工作承接。

同样，历史上曾经提出过的路线不应因为“保持完整目标”而被不断重新激活。要保持可恢复的是当前有效目标及其变更依据，不是所有历史设想。

规划可以重排，但重要历史不通过删除记录来获得“整洁”。

完成一次实施，也不代表上层产品假设已经被证明正确。行为验收、交付结果和目标效果要分开看。

## 12. 方法必须同时防止草率和过度治理

Vision Harness 的价值不只是在条件不足时阻止 Agent，也包括在条件足够时帮助项目继续推进。

### 条件不足时

Agent 应停止越过当前边界，并说明真正缺少什么，例如：

- 授权不足；
- 关键目标或范围未明确；
- 会推翻当前路线的关键假设尚未验证；
- 当前承诺缺少必要 Spec；
- 高风险变更缺少必要审查；
- 证据无法支持准备作出的结论。

不能通过偷偷缩小范围、降低质量要求或改写验收条件让工作“通过”。

### 条件足够时

Agent 不应继续扩大前置工作，例如：

- 愿景已足以支持当前规划，就不继续访谈；
- 当前功能已有清晰 Spec 且不改变架构，就不创建新 ADR；
- 已有 Issue 能覆盖暂缓内容，就不创建重复 Issue；
- 当前改动不影响某项已有证据，就不要求全部重验；
- 远期实现细节未定，但与当前工作无关，就不阻塞当前工作；
- 没有局部差异，就不创建子目录 `AGENTS.md`；
- 小型低风险变更不因为存在审查体系就机械执行全部审查种类。

新增流程要求必须能够说明它针对的风险、触发条件和停止条件。“更完整”“更稳妥”本身不是继续增加治理的理由。

### Vision Harness 自身也必须被验证

Agent 行为评估应同时包含正反场景：

| 应当停止或限制 | 应当继续或简化 |
| --- | --- |
| 用户只要求评估，不得自行实施 | 用户已经授权实施，不应逐步重复确认 |
| 关键前提会改变当前路线且尚未验证 | 只有无关远期细节未决，不应阻塞 |
| 测试全绿但本次承诺仍有遗漏 | 本次承诺和必要验证已满足，应允许结束 |
| 证据对应旧候选，不能支持新结论 | 变化未影响结论且依据明确，可以复用证据 |
| 新方案尚未按规则生效 | 新决定已经生效，不应继续以旧规则阻塞 |
| 已有规则不足以覆盖局部特殊情况 | 没有局部差异，不应创建重复规则 |
| 新增抽象只服务推测性未来 | 当前复杂度有明确需求或可信风险依据 |
| 已知产品是 Plugin，但规划只输出抽象能力分类 | 近期交付已具体，只剩无关远期 Hook 细节未知，应允许继续 |
| Issue 标题增加“Skill”，但正文仍无法说明具体行为和验证 | 已有可用规划，不应新增一层同义能力目录 |
| 用户只要求高层讨论 | 未获得写入授权，不得自行批量创建完整规划 |

评估关注 Agent 的实际决策、操作和结果，而不是 Skill 是否加载、文档是否生成或 Agent 是否口头声称遵守流程。

维护者使用的方法评估能力不属于普通项目的必经流程，但公开入口、直接调用和条件协作仍必须受验证。共同触发次数、文件数和菜单数不能单独证明 Skill 划分合理；还应观察独立结果、责任边界和交接成本。
