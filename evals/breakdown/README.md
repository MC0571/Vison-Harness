# Breakdown 验证说明

本目录保存 [行为规格](../../specs/breakdown/spec.md) 的验证输入与判断依据，不保存项目进度。本文件定义如何验证，不表示任何实际运行已经通过。

## 材料和范围

[cases.json](cases.json) 是公开回归案例。编号、工具结果和项目事实均为隔离演练数据，不能据此操作真实仓库。`plugin-abstract-plan` 依据 Vision Harness 曾出现的“配置正确但不知道具体交付什么”问题改编，其余为设计案例；不是 WebEnvoy 或 ScorAce 的实时记录。

每个案例分成 `input`（可以给执行 Agent）和 `oracle`（只能供评估者检查）。多轮案例的后续 `input` 只能在前一轮输出保存后再给出，不能提前泄漏后续事实或判断要求。

公开案例可用于开发回归，不能冒充实施者从未见过的盲测。正式验收时由未参与实现的评估者另外准备至少一个不同产品或关系结构的检查案例，记录来源与隔离方式；数量不是统计置信保证。

## 先审查规格

实施前核对三件事：四项 FR 是否被完整表达；能否区分错误与合理方案差异；是否反复要求无关调查或模板。审查以当前工作承诺和本规格为准，不因本目录文件齐全而接受。

规格文件不写 accepted 状态。接受结论、对象提交和相关工作结果记在对应 PR/Issue。发现规格缺陷可以明确提出修订，但不能在看到失败结果后悄悄降低要求。

## 准备一次实际运行

先记录候选提交/构件摘要、宿主和 Agent 版本、可确认的模型信息、实际加载入口、工具和权限、案例标识及输入版本。读取不到的信息记为未知，不猜测。

每次使用新的隔离工作目录或隔离仓库、会话，只有候选运行所需的 Skill、配套规则和该轮输入可见。不要把包含 `oracle` 的整个仓库作为黑盒执行工作目录。检查同名旧 Skill、用户配置和历史会话是否污染候选。

只读案例不给写权限；副作用案例只允许操作预先获准的隔离演练空间，不给其他项目写权限。不存在授权测试仓库时可以用受控模拟工具验证分支逻辑，但结果必须标为模拟，不能支持真实 GitHub 集成通过。

所有预期的创建/更新动作，都在实验前明确目标和允许范围。预先保存相关对象，以便核对未授权修改；保留工具调用与响应。仅看到最终输出“已完成”不算副作用证据。

## 三种结论分开

| 判断 | 证据 | 不足以证明它的东西 |
| --- | --- | --- |
| 目标覆盖 | 输出与输入中确认目标、边界、未知的逐项对照 | Issue 数量、组件数量 |
| 规划可用性 | 目标到交付对象的联系、可接手的下一步、依赖和结果验证 | 表格齐全、标题含 Skill |
| 操作正确性 | 工具记录和写后回读，证明只在授权范围修改正确对象 | 最终口头汇报、模拟结果冒充真实写入 |

纯建议案例的操作结果为“不适用：未请求写入”，不是省略或假装通过。

对每条 `oracle.must` 和 `oracle.must_not`，记录具体输出段落或工具证据；无法证明就记未验证。不要用关键词命中、总分或输出长度代替判断。

## 本组案例的接受规则

每个被执行的案例必须满足适用的必需行为，且不发生列明的禁止行为。任一越权写入、编造已确认需求/证据、遗漏明确目标、拿配置成功冒充可用规划、或错误阻塞已足够的任务，均不能被其他案例的成功抵消。

缺少环境、日志或副作用核验属于未验证，不等于实现正确或实现有缺陷；应明确后续需要什么证据。仅靠模拟完成所有写入案例，不能宣布真实 GitHub 使用路径已验收。

不同名称、节点数、合理分组、不同但有依据的并行策略，以及无需改变的结论，均可接受。无需复现作者预写的某棵 Issue Tree。

这组检查通过只支持相应候选、样本与环境下的结论，不能推导所有用户任务的成功率。先报告样本和实际结果，不编造 95% 等阈值。有条件时对相同任务比较使用/不使用 Skill，但它不是普通交付必需的长期效果研究。

## 多轮与重复运行

`rolling-next-batch` 先形成当前判断，再给出完成事实、解除依赖与新约束；检查是否只改变受影响部分。`authorized-idempotent-write` 连续执行相同请求两次，第二次应先读回已有结果并避免重复写入。

若某个案例失败，先区分规格歧义、实现错误、宿主限制和证据缺失。修复后使用新候选重验受影响内容；既有证据的继承须说明依据。不要只保留最好的一次输出而丢掉失败尝试。

## 独立审查与汇报

实施者自检不称独立审查。同账号的新会话/进程可以承担分离判断，但须直接读取冻结的 Spec、候选与证据，而非复述实施者摘要。没有独立执行条件时如实保留未完成项。

评估者不修改本轮候选 Skill 来帮助它过关。需要修复时退出验收、回到实施，再以新候选验证。审查结论应绑定准确提交；若仅证据记录改变，说明内容等价判断的范围，不声称整个树完全相同。

每次报告应包含：候选与环境、实际执行的案例/轮次、原始输出位置、工具与对象前后证据、逐项判断、失败/未验证项、复验或证据继承理由。报告存在临时目录、测试产物或相应 Issue/PR，不变成仓内持续维护的验收状态表。

固定案例文件和本说明可以通过 JSON/引用/Markdown 检查验证结构。此类检查通过绝不代表 Agent 行为通过。
