# 工作入口与条件方法验证设计

本目录验证重构后的工作入口路由、横切方法按条件加载，以及“该停时停 / 条件充分时继续”。它是产品架构、Review 行为约定与 METHOD 的验证投影，不保存项目状态，也不表示候选已经实际运行通过。

## 要验证什么

- 自然用户请求能够到达一个明确工作入口，不重新暴露已下沉的横切方法 Skill。
- Breakdown 的全景、单项、协调三种模式可直接请求，不形成“规划 → shaping → coordination”固定链。
- Spec / Code / PR 都由统一 Review 入口处理，同时保留各对象的判断差异。
- 关键假设、Architecture Impact、complexity control、evidence reuse、review setup 等只在触发条件出现时加载。
- 缺关键目标决定、授权或适用证据时会限制受影响动作；条件充分时会继续，不增加无关治理。
- 入口合并后，原职责仍有可观察结果和验证覆盖。

## 使用方法

cases.json 中 input 可以提供给候选；oracle 与顶层 pairs 仅供评估者。pairs 明确记录本轮需要成对验证的条件差异，装配测试会检查案例输入、must/must_not 判据和配对引用的结构完整性。入口名可作为路由预期，但输出措辞、问题数量和内部推理过程不是唯一答案。

project-startup 继续验证 Vision、接入、接续和授权；breakdown 继续验证完整规划与 rolling refinement。本目录只补本次架构重构引入的入口路由、条件加载和治理比例回归，不重复已有场景。

正式行为验收需要隔离实际候选，记录宿主/模型/工具、准确输入、原始输出和副作用。静态文件检查、装配成功或 Skill 被发现，只能支持对应结构结论。

## 正反成对

Eval 不奖励“治理越多越好”。每个停止判断都应有对应的继续语义：

- 会改变目标的关键决定缺失 → 停受影响部分；无关远期未知 → 继续。
- review-only → 不改候选；明确实施授权 → 不重复索取同一许可。
- 候选变化使旧证据失效 → 补验；变化未触及结论且来源明确 → 复用。
- 存在真实局部差异 → 可以新增局部 Agent 规则；没有差异 → 零写入。
- Architecture Impact 为真 → 做相应设计；既有架构直接承载 → 不制造 ADR。
- 只要求协调方案 → 止于方案；明确授权执行协调 → 继续核验交接并完成统一候选集成。
- 关键未知已有适用证据 → 不制造 probe；证据不足且会推翻路线 → 使用事前判据、有限预算和停止条件的有界试验。
