# 工作入口与条件方法验证设计

本目录验证重构后的工作入口路由、横切方法按条件加载，以及“该停时停 / 条件足够时继续”。它是 [产品架构](../../ARCHITECTURE.md)、[Review 行为约定](../../specs/review/spec.md) 与 METHOD 的验证投影，不保存项目状态，也不表示候选已经实际运行通过。

## 关注的问题

1. 用户自然请求是否落到正确工作入口，而不是重新暴露已下沉的方法 Skill；
2. Breakdown 的全景、单项、协调三种模式能否直接调用，不形成固定串行链；
3. Spec/Code/PR 是否由统一 Review 按对象判断，并保持 review-only 不修改；
4. 关键假设、复杂度控制、evidence reuse、Architecture Impact、AGENTS/review setup 是否只在条件出现时加载；
5. 缺关键决定或授权时是否只停受影响部分；条件充分时是否避免新增 ADR、Issue、规则或全量验证。

cases.json 的 input 可给候选，oracle 仅供评估者。入口名称可以显式作为路由期望，但具体措辞、问题数量和内部推理不是唯一答案。

## 与其他 Eval 的关系

- project-startup 继续验证 Vision、接续、接入、授权和 AGENTS 行为；
- breakdown 继续验证完整规划与滚动细化；
- 本目录重点验证本次 Skill 收敛后没有丢职责、误路由或重新制造治理链。

正式行为验收仍需隔离候选、准确宿主/版本、原始输出与副作用证据。静态文件或装配测试只能证明分发结构。

## 成对判断

任何“停止”案例都要有对应的“继续”语义：缺少会改变目标的决定时停受影响部分；无关远期未知不能阻塞。只授权审查时不改；明确授权实施时不逐步重复确认。旧证据已被候选变化影响时补验；未受影响且来源明确时复用。

新增治理步骤只有在能说明所防风险、触发条件和结束条件时才成立。“加载更多 reference”“跑更多检查”“创建更多文件”本身不是更高分。
