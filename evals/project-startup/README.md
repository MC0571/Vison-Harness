# 项目启动与交接验证设计

本目录验证 [愿景工作](../../specs/vision/spec.md)、[项目接入与接续共享约定](../../specs/project-context/spec.md) 及其与 [Breakdown](../../specs/breakdown/spec.md) 的衔接。它保存固定输入和判断依据，不保存项目状态，也不代表任何 Skill 或 Plugin 已运行通过。

## 与已有验证的关系

共用的候选记录、输入/判据隔离、真实/模拟区分、逐项判断和失败保留规则，沿用 [Breakdown 验证说明](../breakdown/README.md)。不重写一套竞争的验收标准，也不因新增目录就重跑不受影响的 Breakdown 全集。

本组新增关注：愿景充分性与局部授权、方法提供者与消费项目的来源区分、既有布局、持续/撤销委托、新会话恢复、局部规则维护和组件交接。正式 Plugin 获取、包格式与更新保护由对应包路径试验提供证据；语义案例不替代安装试验。

## 案例如何使用

[cases.json](cases.json) 中每个案例包含 `id`、`targets` 和 `turns`。每轮的 `input` 才能交给执行 Agent；`oracle` 只供评估者使用。`session` 为 `new` 时启动隔离会话，为 `same` 时继续该案例上一轮，为 `fresh` 时启动不知道上一轮对话的新会话。

所有项目名称、路径和对象均为隔离演练设定，不是对真实仓库的操作授权。评估者先在获准的临时目录或测试系统中准备对应文件/对象；可从真实工具读取的事实以文件或工具呈现，不用一句“读取成功”冒充实际调用。没有真实写入条件时可验证推理，但必须标为模拟或未验证。

对于 `fresh` 轮，只保留前一轮按授权产生的持久材料，或本轮明确给定的变化快照；不得传入上一轮 transcript、判据、隐藏摘要或后续输入。不同轮次必须按顺序释放；保存前轮输出后才能准备下一轮变化。

候选执行空间只暴露实际分发的 Skill、必要运行参考/脚本和本轮输入。研发 Spec 由评估者用于独立判断；不能为了测试方便向候选额外注入未分发的研发文档。明确排除 oracle、评估者输入和未见案例；研发侧的链接不构成运行时访问授权。

## 先审查设计，再验证实现

规格审查核对当前工作承诺、两份 Spec、与 Breakdown 的职责分界以及正反场景。不同合理文件名、分组和叙述顺序不是失败；缺少必要行为或增加无关阻塞才是问题。

材料接受只支持后续实施。结构检查、作者自检和规格审查不能支持“愿景、接入或接续已经实现”或“首阶段交付通过”。正式行为验收使用实际候选；由与实施判断分离的评估者另备未参与调试的案例。

## 三层验证不能混用

| 层次 | 要取得的证据 | 不能代替什么 |
| --- | --- | --- |
| 包与资源 | 获取/安装/更新日志、包身份、引用解析及消费项目文件前后摘要 | 不证明语义行为正确 |
| 单入口行为 | 对应工作入口的实际输入、读取、输出和副作用 | 不证明整个组合路径成立 |
| 组合用户结果 | 同包候选完成愿景、获准具体规划、无旧聊天接续；记录各入口与实际项目事实 | 不外推所有宿主、模型和长期效果 |

包试验应确认没有依赖源仓库上下文、全局旧 Skill 或用户配置暗中兜底。安装后 Skill 与必要运行参考的读取路径、字节摘要与包候选对应；测试更新前后消费项目的 VISION、AGENTS 和自定义规则不被覆盖。

## 判断与收口

逐项记录 `must`、`must_not` 的原始输出位置或工具证据。区分失败、环境阻塞、未验证和不适用；不得将总分或节点数量作为替代判断。授权越界、确认需求被编造/遗漏、错误阻塞足够明确的任务，不能由其他成功抵消。

愿景确认/写入、规格接受、探索结束、单 Skill 验收和产品交付分别表达。准备工作结束不能关闭仍未完成正式路径验收的交付事项。反过来，无关的远期内容不能成为当前充分结果的阻断。

实际运行前记录候选、环境/版本、模型（可确认时）、权限、输入版本、预算与次数；保留首次失败与修复后的证据关系。产物保存为可访问的测试构件或附件，附文件清单/哈希；在工作记录中给出入口，不生成仓内进度数据库。

## 职责映射与新增多轮回归

`targets` 是语义覆盖标签，不是必须存在的同名 Skill 或菜单。保留既有 `vision`、`project-context`、`breakdown-handoff` 等标签和案例 ID 便于与旧候选比较：

- `vision` 对应 vision-management；
- `project-context` 中的任务/权限/恢复由 using-vision-harness 承担，接入由 project-onboarding 承担，局部指引由 agent-instructions 承担；按具体案例选择，不强制三者一起运行；
- `breakdown-handoff` 是组合范围，`composition` 是集成判断，不新增同名 Skill。

原十五个案例保留。新增案例覆盖愿景多轮等待、用户改主意、可查事实、充分授权下及时持久化、直接调用与局部阻塞；这些是设计输入，不是已经运行通过的结果。评估不把固定问题数量、树形、文件布局或入口总数当正确答案。

多轮 `same` 只按顺序释放本轮信息；未来答案与 oracle 不能提前提供。可查事实须先布置为工具/文件，执行者只见定位线索；只有文字设定的运行不能宣称查证能力已验证。记录有无越权、未确认假设、用户重复纠偏和无必要等待，不用“问题越多”或“流程越全”证明质量。

用共享契约审查每个直接入口，并用明确条件测试交接/返回。只在已确认任务需要时组合；已有清晰缺陷不得先跑愿景与全局规划，局部架构调整不得阻塞不受影响工作。维护者方法评估不进入普通用户的运行时包，候选不能读取评估者判据。
