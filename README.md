# Vision Harness

**帮助用户把软件项目的目标说清楚，并让编程 Agent 在不丢整体目标的前提下可靠、高效地持续交付。**

Vision Harness 是一套面向 AI 编程 Agent 的软件工程方法，通过 Plugin 和 Skill 融入现有编程 Agent 工作环境。

它不是新的项目管理平台，也不是一套要求你手工维护大量文档的流程。它主要帮助用户和 Agent 做五件事：

1. 把模糊想法澄清成足以支持规划的项目愿景；
2. 保持完整目标可见，同时只细化当前真正需要推进的部分；
3. 看清依赖关系，安排合理的串行、并行和集成方式；
4. 按实际变化选择 Spec、架构、TDD、审查和质量验证，并抑制没有依据的复杂度；
5. 用授权和证据判断何时继续、何时完成、何时调整或停止。

项目的完整愿景见 [VISION.md](VISION.md)，详细方法规则见 [METHOD.md](METHOD.md)。

## 当前提供的实现

`vision-harness` Plugin 候选 `0.2.0-alpha.1` 已为架构中的一个入口和十八类用户工作提供 Skill 指令及分发文件。维护者的 `method-evaluation` 位于研发仓库，不装配进普通用户 Plugin。这里说明的是已经提交的实现范围，不代表新增能力已经通过运行验收。

| 工作范围 | 已提供的 Skill 实现 |
| --- | --- |
| 入口、接入与愿景 | `using-vision-harness`、`project-onboarding`、`vision-management` |
| 调查、规划与协调 | `assumption-validation`、`breakdown`、`issue-shaping`、`delivery-coordination` |
| 规格、设计与实施 | `spec-development`、`technical-design`、`tdd-development`、`simplification` |
| 审查、验证与交付 | `spec-review`、`code-review`、`pr-review`、`change-verification`、`release-delivery` |
| 纠偏与规则维护 | `project-convergence`、`agent-instructions`、`review-setup` |

安装、工作入口和开发装配命令见 [Plugin 使用说明](plugins/vision-harness/README.md)。各 Skill 提供工作方法、条件分支、交接和结束判断；按任务选择，不执行十九步流水线。工具操作由宿主已有能力承担，不新增自有调度器、权限系统或项目数据库。

## 从一个模糊想法开始

用户可以只带着一个不完整的想法进入，不需要提前准备好 `VISION.md`。

例如，下面的目标体验需要真实等待用户回答，不是 Agent 自己补全对话：

```text
用户：
我想做一个帮助团队运行和评估 AI Agent 的项目，希望复用团队已有工具。
先讨论目标，不创建实施任务。

Agent：
“运行”是指提供运行环境，还是检查和指导现有环境？
这会改变产品的主要职责。根据你希望复用现有工具的要求，
我建议先考虑后者，但需要你确认取舍。

用户：
指导现有环境，不接管运行时。主要给长期维护项目的人使用。

Agent：
已明确：使用者是长期维护者，不建设运行时。
接下来需要决定的是他们最难完成的任务，而不是部署方案。
哪些实际失败最值得优先解决？
```

Agent 应自行核对可查事实，只追问影响当前取舍的决定；推荐不是用户答案。已知内容不重复问，前提变化只重开相关讨论。理解足够时总结确认与未知；已授权记录就保存到项目已有权威愿景入口，仅讨论则在总结处结束。不强制问卷、固定轮数或额外确认手续。

Vision Harness 应帮助用户形成一份合格的 `VISION.md`，但“合格”不等于篇幅长或标题齐全。

它只需要足以支持后续取舍：使用者与问题、预期结果、主要能力、产品边界、明确不做的内容、成功表现，以及仍需验证的关键未知。

这些信息已经足够时，就应该进入下一步，不为了“更完整”无限访谈。

## 从愿景进入工作规划

Vision Harness 不把一句愿景直接转换成大量工程任务。它应先连接目标、结果证据和具体产品交付，再逐步细化近期工作。

以 Vision Harness 自身为例，规划方法可以表达为（这是方法示例，不是当前版本的验收记录）：

```text
VISION
  ↓
阶段目标：
Breakdown 能把愿景变成具体、可接手的产品规划
  ↓
结果证据：
- 用户无需再次把抽象能力翻译成产品组件
- 新 Agent 能直接继续下一层拆解
  ↓
具体产品组成：
- Breakdown Skill
- 必要参考材料
- 宿主接入与 Hook（仅在验证后确认需要的部分）
- 行为评估
  ↓
Milestone
  ↓
FR / Issue
  ↓
当前批次细化到可进入 Spec / 实施
```

具体产品组成应该在规划中可见；实现细节可以逐步确定。不能为了“不提前设计”而连主要交付对象都不说明。

Breakdown 保留现有名称，承担整体规划与滚动细化；候选名称 roadmap-planning 不另外生成同义入口。仓库级接受与实际分发、单项整理及执行期协调分别验收。Hook 根据具体自动触发需要选择，不是每个 Skill 必须配置的组件。

已确认但暂不实施的能力要保持可追踪，但不要求每个细节都单独建立 Issue。已有合适的能力 Issue 能覆盖，就不重复创建。

## 按工作选择能力

完整职责是一个入口、十八类工作和维护者方法评估，不是二十步流水线。具体映射与协作见 [产品架构](ARCHITECTURE.md)。例如：

| 用户请求 | 对应工作与停止位置 |
| --- | --- |
| “继续这个 Issue” | 入口只恢复相关事实和权限，选择当前工作；不重做愿景或项目初始化 |
| “把已有仓库接入这套方法” | project-onboarding 查真实缺口，按需组合愿景、规划、指引或审查配置；已有内容足够就复用 |
| “这项任务到底做到哪里？” | issue-shaping 整理单项承诺，不重新规划整个产品 |
| “这几项工作怎样更快交付？” | delivery-coordination 处理真实依赖、分工和集成；未授权实施就停在方案 |
| “只审查 Spec / 代码 / PR” | 分别选择对应审查；验证获取证据，审查形成判断，不自动修复、合并或发布 |
| “这些规则太重了” | simplification 诊断复杂度及成本；需要改指引或审查配置时交给相应维护工作 |

完整设计中的每个工作 Skill 都应可被直接调用，仍要核对自己的依据与授权。入口不是必经关卡，也不凭它的存在就承诺宿主会自动加载。具体调用取决于宿主实际加载的候选；缺失入口应明确报告，不能假称已执行。

## 帮助安排依赖和并行

父子 Issue 只表示工作归属，不自动表示执行顺序；优先级也不等于依赖关系。

Vision Harness 应帮助用户和 Agent 说明：

- 哪项工作真的需要另一项结果才能继续；
- 依赖阻塞的是开始、集成、验收还是发布；
- 哪些准备工作可以先做；
- 哪些工作可以并行；
- 并行工作共享什么约定，各自允许修改什么；
- 最后由谁、以什么顺序集成，并在同一候选结果上重新验证。

例如：

```text
当前目标：增加“暂停任务”。

先统一：
- 暂停状态及转换规则
- 对外调用约定

可以并行：
- 执行端处理暂停请求
- 调用端增加暂停入口
- 准备暂停、恢复、取消互相影响的测试

集成前：
- 合并到同一候选版本
- 验证真实调用路径
- 检查暂停与取消的冲突行为
```

并行不是目标。如果协调成本、共享修改冲突或最终集成风险高于收益，就应该减少并行。

## 接管已有项目

对于已经存在的项目，Vision Harness 不应重建一套目录和流程。

典型交互可以很简单：

```text
继续处理 #37。

Agent：
我先读取当前 Issue、相关 Spec、适用的 AGENTS.md、架构约定和已有验证。

#37 已经明确：
✓ 目标和当前范围
✓ 相关 Spec
✓ 授权允许修改代码和测试
✓ 没有未解决的前置依赖

本次没有改变长期架构，不需要新 ADR。
已有信息已经足够，我直接进入实施，不重新规划整个项目。
```

如果再次执行同一方法，而项目事实没有变化，Vision Harness 不应该生成重复 Issue、重复 Spec、重复审查材料或无意义的文档更新。

## 授权范围决定 Agent 能做什么

“知道下一步应该做什么”和“获准执行下一步”是两回事。

例如：

```text
你：
评估一下我们要不要替换当前缓存方案，只给建议，不改代码。

Agent：
我会调查现有约束、风险和替代方案。
本轮可以读取和分析，但不会创建实施 Issue、修改产品代码或提交 PR。
```

如果用户已经明确授权“完成这个 Issue，提交到独立分支，但不要合并”，Agent 就应在这个范围内连续推进，不必每一步重新确认；到合并边界时再停止。

## 项目中的事实放在哪里

Vision Harness 不建立自己的状态数据库。同一种事实只维护一个权威位置，其他地方引用它。

| 内容 | 常见维护位置 |
| --- | --- |
| 项目长期目标 | `VISION.md` 或项目已有的权威愿景入口 |
| 路线图、Milestone、优先级、负责人、工作状态 | GitHub |
| 能力、功能、暂缓工作、父子关系和依赖 | GitHub Issue |
| 长期行为规则 | Spec |
| 当前长期架构 | `ARCHITECTURE.md` 或架构文档 |
| 重大长期技术决策的原因 | ADR |
| 一次变更的技术方案 | GitHub |
| 需要独立安排、协作或验收的执行工作 | GitHub 子 Issue |
| 项目级 Agent 工作约定 | `AGENTS.md`，按项目需要分层 |
| 审查方法 | 项目已有审查规范、Skill 或宿主支持的配置 |
| 当前实现 | 代码 |
| 可执行保证 | 测试 / Schema / Contract |
| 一次审查、验收或授权记录 | 对应的 Issue、PR、审查记录或项目既有载体 |

Vision Harness 默认不要求维护与 GitHub 平行的 `ROADMAP.md`、`tasks.md` 或自己的 `state.yaml`。已有项目中的纯导航、自动生成视图或明确非权威的摘要可以保留，只要它们不成为另一份需要手工同步的事实来源。

一个项目可能长成：

```text
/
├── VISION.md
├── AGENTS.md                    # 有全仓 Agent 约定时
├── ARCHITECTURE.md              # 需要长期架构说明时
├── specs/
│   ├── execution-engine/
│   │   ├── spec.md
│   │   └── state-model.md
│   └── authorization/
│       └── spec.md
├── docs/
│   ├── adr/
│   └── review/                  # 项目确实需要长期审查规则时
│       ├── spec-review.md
│       ├── code-review.md
│       └── pr-review.md
├── .codex/
│   └── agents/                  # 使用 Codex 子 Agent 且确实需要时
├── src/
└── tests/
```

这只是可能的组织方式，不是固定模板。

## 处理一个具体 Issue

Vision Harness 会根据现状选择需要的方法，而不是机械套完整流程。

```text
Issue
  ↓
确认本轮承诺与授权
  ↓
读取足以支持当前决定的目标、规则和相关事实
  ↓
检查真实依赖与关键未知
  ↓
只更新被当前变化影响的 Spec / 架构 / 项目约定
  ↓
选择串行、并行和集成方式
  ↓
按行为切片执行 TDD
  ↓
执行与风险相称的审查和验证
  ↓
核对本轮承诺、证据和授权边界
  ↓
继续 / 交付 / 调整 / 停止
```

如果只是内部重构，可能根本不需要修改 Spec。

如果技术选择会长期约束多个后续功能，才考虑记录 ADR。普通实现选择不需要。

如果现有事实已经足够，就直接推进；不能因为远期规划尚未完成或无关文档不齐全而扩大前置工作。

## Vision Harness 也帮助减少复杂度

“更完整”和“更稳妥”不能自动成为增加工程复杂度的理由。

Agent 在增加抽象、兼容路径、防御逻辑或流程要求时，应能够回答：

> 这项复杂度服务于哪项已确认需求、可信风险或明确维护需要？更简单的方案为什么不够？

Vision Harness 应主动指出：

- 没有改变行为时，不需要新建 Spec；
- 已有 Issue 已经覆盖暂缓能力时，不需要再建重复 Issue；
- 已有架构可以直接承载当前功能时，不需要新 ADR；
- 风格偏好或推测性未来需求，不应自动成为阻断；
- 有效证据没有受到当前变化影响时，不应无理由全部重跑。

但“简化”也不能成为删除必要权限检查、数据保护、错误处理或真实质量验证的借口。

## 测试全绿为什么还不一定完成

测试只能证明已经写下来的行为通过了。

如果 Spec 要求：

```text
- 可以超时
- 超时后不能再次变成“已完成”
- 超时状态必须持久化
```

而 Agent 只写了前两项测试，那么所有测试都可以是绿色，但工作仍然少了一项。

反过来，如果本次范围与必要验证都已经满足，也不能仅因为长期能力还有远期内容，就否定这次交付。

因此，Vision Harness 要求结论与承诺层级匹配：

- 探索任务完成，不等于功能已交付；
- Spec 已接受，不等于代码已实现；
- 当前切片完成，不等于长期能力完成；
- 长期能力未完成，也不等于当前版本不能交付；
- 审查通过，不自动等于已经获得合并或发布授权。

## Vision Harness 不做什么

Vision Harness 不提供仪表盘、可视化、路线图数据库、自有 Issue 跟踪系统或自有工作流状态引擎。

它不会强迫所有项目生成相同的 Spec、`AGENTS.md` 或审查文件，不会把每个技术选择都写成 ADR，也不会要求所有工作都经过固定数量的 reviewer 或子 Agent。

它是一套帮助 Agent **更准确地判断和推进工作**的方法论工具，而不是另一套项目管理软件。
